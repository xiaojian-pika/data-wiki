### Type (model/dataset/toolchain/evaluation benchmark)

All seven are academic papers in form, but fall into four categories by nature:
【Foundation model category】ALIVE (a complete T2VA/R2VA foundation model with VideoDiT 12B + AudioDiT 2B, accompanied by the Alive-Bench 1.0 evaluation benchmark), NAVA (a 6.3B natively-aligned joint generation model, with open-sourced weights and training code).
【Module/method category (enhancements atop an existing foundation)】Baton (a VA-Planner semantic planner + RS-RoPE prepended before the joint DiT denoising process, a method-level enhancement), CCL (four module-level improvements — TARP/LCT/DCR/UCG — targeting the dual-stream Transformer paradigm, focused on saving data and compute).
【Task + dataset category】OmniCustom (proposes the new task of "synchronized audio-video customization"; one of its core contributions is the self-built OmniCustom-1M dataset, paired with a 100-example evaluation set).
【System/engineering category】StreamChar (a long-horizon streaming generation system, including two-stage distillation and a real-time inference pipeline).
【Inference-time algorithm category】ITS-JAVG (a fully training-free inference-time scaling algorithm + a study of multi-verifier combinations + the ARW optimization algorithm, with no model training at all — essentially "using evaluation models to do inference-time data selection").
From a data-research standpoint: ALIVE, NAVA, and OmniCustom disclose substantive data-processing pipelines; Baton, CCL, and StreamChar disclose only a list of data sources; ITS-JAVG has no training data, but its "verifier combination" thinking is highly isomorphic to data quality-scoring gatekeepers.

### Degree of Openness (whether weights/code/data/pipeline are each open-sourced) ⚠️

Openness varies enormously, ranging from fully open-source to technical-report-only:

Dependent components reuse the Wan2.2-5B VAE, T5 encoder, LTX audio-VAE, and the ReDimNet speaker embedder (each governed by its own original license). Not open-sourced: the training data itself and the data-processing pipeline code (the repository explicitly mentions training data but no data pipeline has been released).
【Medium ｜ OmniCustom】Provides a GitHub repository and a project homepage; code is available. Its self-built OmniCustom-1M is derived from the public dataset SpeakerVid-5M, so the data-construction process is reproducible (all filtering rules are public), but whether the post-filter list itself has been released is unclear [uncertain].
【Medium ｜ StreamChar】Has a project homepage at humanaigc.github.io/StreamChar_page/; all training data comes from three public datasets (SpeakerVid-5M / TalkVid / OpenHumanVid) plus Emilia, so the data side is highly reproducible; the release status of weights and code is unclear [uncertain].
【Leaning closed ｜ ALIVE】The GitHub repository FoundationVision/Alive currently serves only as a technical-report landing page (containing an assets directory, an arXiv link, a project page, and a Discord demo entry); no weight downloads, training code, inference code, or data release have been observed. Alive-Bench 1.0 (264 general prompts + 90 reference-character prompts) has been defined in the paper, but its public-release status is unclear [uncertain]. It is the work with the most detailed data disclosure and the lowest code openness among the seven.
【Closed ｜ Baton / CCL】Paper only; the training data includes an in-house / internet self-collected portion that is not open-sourced; CCL's in-house data (interviews, short dramas, films) is explicitly not obtainable.
【N/A ｜ ITS-JAVG】Training-free, so no weights need to be open-sourced; the paper states "Project materials and code are available online," so the code and prompt set should be obtainable [uncertain: the specific repository address has not been verified]. The verifiers it depends on (VideoReward, JavisScore, ImageBind, VQAScore, AVHScore) and the base generators (JavisDiT, MMDisCo, LTX-2) are all already open-sourced assets, giving it the highest reproducibility.

### Whether Joint Audio-Video Generation Is Supported, and How It Is Implemented (native joint / cascaded / MoE fusion)

All seven works revolve around joint audio-video generation, but their implementation paths fall into five categories, which together form a cross-section of the 2026 JAVG technical landscape:
(1) 【Native joint + upfront semantic planning】Baton: before the joint DiT denoising process, a VA-Planner (a multimodal LLM based on Qwen3-8B, with dual semantic alignment towers) first generates a batch of "planned tokens" as a shared audio-video semantic blueprint, then injects the blueprint into the denoising process using Relative Semantic RoPE (RS-RoPE). Its core argument is that "existing methods rely on coarse-grained embeddings from off-the-shelf text encoders, losing fine-grained semantics and lacking shared long-horizon planning." The planner does not predict discrete tokens but instead regresses continuous features (L2-regressed to the penultimate-layer features of a frozen SigLip2 video encoder and a frozen WavTokenizer audio encoder), on the grounds that "regressing continuous features preserves richer semantic structure."
(2) 【Native joint + customization LoRA】OmniCustom: on top of an existing joint audio-video generation foundation model, two independent LoRAs (a reference identity LoRA and an audio timbre LoRA) act on the self-attention layers respectively, enabling "given a reference image + a reference audio clip, generate synchronized audio-video that preserves that identity, mimics that timbre, and speaks the lines specified by the prompt." It additionally introduces a contrastive learning objective (the prediction stream with reference conditioning as the positive example, the one without reference conditioning as the negative example) run in parallel with flow matching.
(3) 【Streaming autoregressive + decoupled orchestration】StreamChar: decouples "long-horizon orchestration" from "short-window denoising" — an LLM orchestrator reads the full transcript and historical context and produces frame-aligned audio conditioning; the joint audio-video DiT performs bidirectional denoising within a local window, conditioned on a reference frame and a motion frame. Each chunk outputs 33 frames @24fps, with a historical audio-context cap of 15 seconds, paired with a progress-aware pointer (PAP, supervised with smooth L1 loss on ground-truth end indices derived from ASR timestamps) and a persistent visual anchor (sink chunk) to suppress long-range drift. Runs in real time on a single H100, capable of continuously generating a 5-minute stream.
(4) 【Dual-tower native joint (large-company foundation model)】ALIVE: a unified audio-video synthesis model adapted from a pretrained T2V model, VideoDiT 12B + AudioDiT 2B, supporting Text-to-Video&Audio and Reference-to-Video&Audio (animation). The key architectural components are TA-CrossAttn (temporally-aligned cross-modal fusion) and UniTemp-RoPE (unified temporal RoPE for precise audio-visual alignment). Two tiers: a 480p base model plus a 1080p refiner.
(5) 【Patching the dual-stream Transformer paradigm】CCL: does not change the paradigm, but specifically diagnoses and fixes three classes of defects in dual-stream Transformers — model-manifold drift caused by the gating mechanism, bias introduced by cross-modal attention in multimodal background regions, and inconsistency between multimodal CFG training and inference. Addressed by four modules: TARP (Temporally-Aligned RoPE and Partitioning), LCT + DCR (a stable unconditional anchor and dynamic routing of cross-modal information), and UCG (Unconditional Context Guidance, for inference consistency). Its biggest selling point is reaching SOTA with far less data and compute than comparable work.
(6) 【Align-then-Fuse native alignment】NAVA: explicitly argues against two existing designs — dual-tower designs, which weaken fine-grained synchronization, and unified tri-modal designs, which conflate semantic alignment with low-level alignment. Instead adopts an Align-then-Fuse MMDiT: it first establishes audio-video correspondence in a dedicated alignment space, then injects context (text, speaker embeddings) as an external condition into the shared denoising process via cross-attention. Comes with Timbre-in-Context Conditioning, which binds reference-timbre cues to their corresponding speech spans, supporting multi-speaker reference-timbre control. 6.3B parameters, native stereo output, supports T2AV / I2AV / T2A.
(7) 【Inference-time scaling (no model changes)】ITS-JAVG: transplants inference-time scaling from single-modality domains to joint audio-video generation, fully training-free. The core finding is that a single verifier inevitably leads to verifier hacking and asymmetric trade-offs among metrics, so a combination of multiple verifiers is required; it also proposes Adaptive Reward Weighting (ARW), treating reward aggregation as an online optimization problem. It can be viewed as replicating, at inference time, the "joint multi-scorer filtering" idea from training-data pipelines.

## Data Scale and Distribution

### Training Data Volume (number of video clips/hours/tokens, pretraining and SFT reported separately) ⚠️

The scale of each work spans more than two orders of magnitude, and the disclosure conventions differ:
【ALIVE (Bytedance, the largest in scale and the most finely staged in its disclosure)】Gives sample counts by training stage rather than hours:
- Audio T2A Stage I: 384M audio samples (corresponding to 700k hours of transcribed speech, used for TTS pretraining)
- Audio T2A Stage II: 19M samples (about 5k hours of high-quality speech + 111k hours of video datasets with sound annotations)
- T2VA joint training: 11M samples @480p/24fps (1.2 epochs)
- T2VA+I2VA: the same 11M samples (0.3 epochs)
- Continue-training: 4.3M balanced samples (3 epochs)
- SFT: 5M samples (0.5 epochs)
- 1080p Refiner: 0.7M high-clarity samples (1 epoch)
- Character-driven: 0.8M reference-paired samples
The paper describes this as "continue pretraining and finetuning on million-level high-quality data." The total size of the original candidate pool is not disclosed [uncertain].
【NAVA (Baidu)】The only work to give both ends of the full funnel: the original collection is "approximately 20M audio clips and 100M video clips," filtered down to "around 15M clips for large-scale training" used for large-scale training; of these, the Koala-36M subset accounts for about 20% of the final corpus. The SFT stage further converges to 160K high-quality samples. Average video duration is about 7 seconds (estimated at roughly 29,000 hours based on 15M×7s [this conversion is an inference and uncertain]).
【CCL (SenseTime-affiliated)】Focuses on small data: Table 1 explicitly lists its own training data volume at 4M, placed side by side with Ovi's 30.7M and MOVA's 50M — i.e., using about 1/8 of Ovi's data volume and about 1/12 of MOVA's. The body text describes this as "million-level audio-video pairs."
【Baton】1.5 million video-audio clips; the original text states "Our training dataset (1.5 million video-audio clips) is aggregated from OpenHuman-Vid, AudioCaps, WavCaps, and videos collected from the internet." — one of the smallest training scales among the seven joint-generation works.
【OmniCustom】Self-built OmniCustom-1M: about 1 million single-person video clips totaling 2,500 hours, filtered from SpeakerVid-5M (originally "more than 5.2 million video clips" / "8,000 hours"). That is, a clip-level retention rate of about 19% and an hour-level retention rate of about 31% (2500/8000).
【StreamChar】No total figure is given, only sources (a combination of SpeakerVid-5M + TalkVid + OpenHumanVid) and training step counts (orchestrator: 80k steps @batch 640; joint training: 100k steps @batch 128). Emilia is used for speech pretraining. It explicitly states the constraint that "training data contains no videos/transcripts longer than 20 seconds" [total scale uncertain].
【ITS-JAVG】No training data (training-free); "data volume" is instead reflected in the inference search budget: JavisDiT samples 5 samples per prompt (Best-of-N), MMDisCo samples 10 samples per prompt.

### Composition of Data Sources (proprietary/public datasets/web crawling/licensed acquisition/synthetic data) ⚠️

A clear two-stage pattern of "public dataset reuse + proprietary/crawled supplementation" is evident, with OpenHumanVid and SpeakerVid-5M becoming two de facto standard upstream sources in the 2026 JAVG field:
【Baton】A four-way mix of OpenHuman-Vid + AudioCaps + WavCaps + internet-collected videos, with no description of licensed acquisition or synthetic data.
【OmniCustom】A single upstream: SpeakerVid-5M (a public two-person audio-video interaction human-generation dataset), from which OmniCustom-1M is filtered using self-built rules. The evaluation set additionally includes 70 YouTube video segments + 30 real people not appearing in the training set.
【StreamChar】A combination of three public human/talking-video datasets: SpeakerVid-5M (large-scale, high-quality two-person audio-video interaction human generation), TalkVid (large-scale, diverse audio-driven talking-head synthesis), and OpenHumanVid (large-scale, high-quality human-centric video generation); on the speech side, Emilia, a large-scale multilingual speech dataset. All are public data, making this the most "academically reproducible" work among the seven in terms of data sources.
【ALIVE】No specific dataset is named; described as a proprietary large-scale corpus filtered from a "raw data pool" for "videos with audio." The audio side includes 700k hours of transcribed speech (suspected to be Bytedance's internal Seed speech corpus [uncertain]), 5k hours of high-quality speech, and a 111k-hour video dataset with sound annotations. There is also substantial synthetic/augmented construction (see synthetic_data_synthesis). Overall dominated by internal corpora.
【CCL】OpenHumanVid (public) + in-house collections, with the latter explicitly covering "interviews, short dramas, and films" — a quite specific source profile indicating a bias toward "narrative content with people speaking"; the audio pretraining additionally introduces the academic datasets WavCaps and VGGSound.
【NAVA】A three-way composition: Koala-36M (a public large-scale video dataset, about 20% of the final corpus) + TED-style speech videos (a high-quality single-speaker speech source) + raw movie/TV footage. This is the only work among the seven to explicitly state "raw movie/TV footage" as a source.
【ITS-JAVG】No training data; evaluation uses the VGGSound test set and JavisBench-mini.
【Common observation】None of the seven disclose the proportion of licensed data, and none use C2PA-style provenance; four works (Baton/CCL/NAVA/ALIVE) all contain internet self-collected content or raw movie/TV footage — this is where compliance risk is concentrated.

### Data Compliance and Provenance (proportion of licensed data, rights-cleared datasets, C2PA, etc.) ⚠️

[Uncertain] — none of the seven works discuss the proportion of licensed data, rights-cleared datasets, C2PA watermark provenance, or copyright-compliance review processes. Indirect facts that can be inferred:
(1) Works that depend on public academic datasets (OmniCustom depends entirely on SpeakerVid-5M; StreamChar depends on SpeakerVid-5M/TalkVid/OpenHumanVid/Emilia; Baton and CCL partly depend on OpenHumanVid/AudioCaps/WavCaps/VGGSound; NAVA depends on Koala-36M) effectively outsource compliance responsibility to the upstream datasets — and most of these upstream datasets are themselves based on YouTube scraping, which is itself a source of controversy.
(2) Works that explicitly contain high-risk sources: NAVA's "raw movie/TV footage" (raw film and television footage, the most copyright-sensitive), CCL's "short dramas and films," and Baton's "videos collected from the internet." None of the three include any copyright statement.
(3) On the privacy side: OmniCustom and StreamChar are both face+timbre customization tasks that directly involve biometric data (facial identity + vocal timbre). OmniCustom's evaluation set deliberately uses "30 persons who were not included in training data" to verify zero-shot generalization, but does not mention portrait-rights/voice-rights authorization; ALIVE's character-driven pipeline heavily uses ArcFace facial embeddings for identity matching, likewise with no privacy statement. This is a shared gap in data compliance across this batch of works.
(4) The one clear point on licensing is NAVA: the source code is under Apache 2.0, but the repository explicitly states that "the model weights, pretrained backbones, tokenizer, audio VAE, speaker encoder, and prompt-rewriting model may be subject to different licenses from their respective original providers" — i.e., the license covers the code, not the data.

### Clip Duration Distribution and Splitting Strategy ⚠️

The duration strategies of each work are highly differentiated, reflecting their respective task positioning:
【Fixed-length short clips ｜ OmniCustom】A strictly fixed-length design coupled with "reference-training pairing": videos are first filtered to remove "videos shorter than 10 seconds," and then from each clip of ≥10 seconds, "the first 4 seconds as the reference audio" is taken, while "the last 5 seconds ... [is] designated as both the training audio and video clips" — i.e., one 10-second source clip simultaneously yields a 4-second reference audio and a 5-second training sample, both sharing the same timbre but with different speech content ("each reference-training pair shares the same timbre but contains distinct speech content"). This is a very clean "same-timbre, different-content" pairing construction method.
【Short clips + long sources ｜ ALIVE】The character-driven data extracts N clips of "3–10 seconds" from "long videos (10–30 minutes)"; generated output is 5 to 10 seconds. The identity anchor is taken from the "1.5-second sub-clip with maximum sync score" — i.e., the 1.5-second sub-clip with the highest sync score is used as the source of the identity-representative frame. The overall duration distribution of the training data is not disclosed [uncertain].
【Average 7 seconds ｜ NAVA】Explicitly states "The average video duration is about 7 seconds," the only work among the seven to give an average duration. At inference time, the default is 37 frames @24fps (about 1.5 seconds), which is configurable.
【Streaming chunks ｜ StreamChar】The most unusual duration strategy — on the training side, constrained by "training data contains no videos/transcripts longer than 20 seconds" (no training video/transcript exceeds 20 seconds), while at inference time it must generate a continuous 5-minute stream, achieved by chunk concatenation (each chunk 33 frames @24fps ≈ 1.375 seconds), with a historical audio-context window capped at 15 seconds. This constitutes a striking "trained short, inferred long" generalization gap, and is also the fundamental reason its progress-aware pointer and persistent visual anchor anti-drift mechanisms exist. In evaluation, "150 clips generating 10s audio-video pairs" and "50 clips paired with randomly sampled transcripts (>300 words) to produce 5-minute continuous streams."
【Fixed short duration ｜ ITS-JAVG (evaluation side)】Each tested foundation model has its own fixed duration: JavisDiT generates 4-second videos, MMDisCo generates 2-second videos.
【Not disclosed ｜ Baton, CCL】Baton's Sem100 evaluation set consists of "100 unseen videos (10 seconds long)"; training clip duration is not stated [uncertain]; CCL does not mention duration distribution at all [uncertain].
【Splitting strategy】Only NAVA mentions that "raw videos are first segmented at scale with a Hadoop-based pipeline" (large-scale Hadoop-pipeline segmentation); none of the others describe a splitting strategy [uncertain].

### Resolution/Aspect-Ratio Distribution and Bucketing Strategy ⚠️

Only a few of the seven disclose this, and most commonly adopt a two-tier "low-resolution training + high-resolution refinement" strategy rather than bucketing:
【ALIVE】Explicitly two-tier: the base model is trained at 480p/24fps on 11M samples, with a separate 1080p Refiner stage trained for 1 epoch on 0.7M "high-clarity samples." This is a typical "large-scale low-resolution base + small-scale high-resolution purification" curriculum. Aspect-ratio distribution and bucketing strategy are not disclosed [uncertain]. ALIVE also has a dedicated clarity-filtering stage, using "reference images across six distinct clarity levels" (six clarity tiers from blurry to sharp) as an evaluation benchmark — essentially turning resolution/clarity into a six-level ordinal label rather than a continuous score, a practice rarely seen among contemporaneous works.
【OmniCustom】Fully unified normalization, no bucketing: "All videos are recorded in 480p at 24 FPS. We extract audio files from videos and unify them into 16kHZ." — video is unified to 480p/24fps and audio unified to 16kHz. This is consistent with its narrow task positioning of single-person talking heads.
【CCL】Training resolution of 352×640p (a non-standard resolution, close to 9:16 portrait), the only work among the seven to give an exact pixel size; single-resolution training, no bucketing.
【NAVA】Training-side resolution distribution is not disclosed [uncertain]; the inference-time default is 704×1280 (9:16 portrait), and the repository states "flexible aspect ratios supported," indicating multi-aspect-ratio capability, though the training-side mixture is not stated.
【ITS-JAVG (evaluation foundation models)】JavisDiT is 240p, MMDisCo is 256×256 — reflecting that the resolution of open-source academic JAVG foundation models still lags significantly behind industry.
【Baton, StreamChar】Resolution/aspect-ratio strategy not disclosed [uncertain].
【Common pattern】None of the seven adopt Ovi-style "equal-area normalization" or Seedance-style multi-resolution bucket scheduling; the general pattern is single-resolution training plus optional high-resolution refinement, indicating that this batch of works is relatively conservative in both compute budget and engineering complexity.

### Category/Domain Distribution and Mixture Strategy (proportional control and concept balancing for people, actions, scenes, styles, etc.) ⚠️

On this dimension, ALIVE and NAVA each establish an explicit taxonomy system, making them the most valuable in this entry; the other five have essentially no mixture control.
【ALIVE — a three-tier tagging system + active proportion adjustment (the most complete domain-control design in this batch)】
(1) Top-level binary split: first a division is made between the core scenarios of "speaking" and "non-speaking" — original text: "First, we make a top-level distinction between core scenarios: 'speaking' and 'non-speaking' scenario." This binary split directly determines the model's mixture of capability between "dialogue-driven" and "sound-effect-driven" abilities.
(2) Three-tier hierarchical tags: on top of this, a three-level hierarchy is built, with Level 1 comprising nine broad domains: Animals, Home Sounds, Entertainment, Environment, Food, Nature, Sound Effects, Vehicles, and Sports. Note that these nine categories form an "audio-visual joint taxonomy" rather than a purely visual taxonomy — Home Sounds and Sound Effects are themselves acoustic categories, indicating that this taxonomy was designed from the outset to serve joint audio-video modeling.
(3) Audio-visual keyword binding: every Level-3 visual tag is paired with a corresponding audio keyword via "joint audio-visual keyword retrieval," forming paired indices between visual concepts and sound concepts — this is the key mechanism that makes domain distribution and audio distribution jointly, rather than independently, controlled.
(4) Active proportion adjustment: original text: "Guided by prior knowledge, such as concept frequency and projected application scenarios, we then adjust the data proportions for each category." — proportions of each category are actively adjusted based on two priors: concept frequency and anticipated application scenarios. The 4.3M "balanced samples" used in the Continue-training stage are the product of this proportion adjustment. Specific percentages are not disclosed [uncertain].
【NAVA — five audio-driven content categories】Uses YAMNet audio classification + an omni-modal tagger to divide clips into five categories: single-speaker speech, multi-speaker speech, ambient sound, music, and singing. Note that its classification axis is acoustic rather than visual, unlike ALIVE's dual visual-audio axis. The proportion of each category is not disclosed [uncertain]. There is also VLM-based filtering and tagging to retain clips with clear visual quality; the tagging system is not detailed.
【CCL — an implicit domain profile】No explicit proportion control, but its data sources — "interviews, short dramas, and films" — themselves constitute a narrow but deep domain: human-centric, dialogue-dominated narrative content. This explains how it achieves SOTA with only 4M data — trading breadth for depth. Its multi-task training probability distribution (see stage_data_mixture), with a high 0.6 share for joint generation, also indicates its target domain is highly focused.
【OmniCustom — a single domain】Entirely focused on "single-person video clips," with no domain-diversity aspiration; its full one million clips fall into the same category. The evaluation set deliberately controls the gender ratio at "1:1" — the only explicit demographic mixture control among the seven.
【StreamChar — a single domain】Human-centric character talking videos, all three upstream datasets being human-centric, with no cross-domain mixture.
【Baton】No domain-mixture strategy is mentioned at all; the mixture ratio among its data sources (OpenHuman-Vid human bodies + AudioCaps/WavCaps general audio + internet videos) is not disclosed [uncertain].
【ITS-JAVG】No training data; but its evaluation benchmark JavisBench-mini itself carries a multi-category structure (inherited from JavisBench's scene/event classification system), used to examine how each verifier performs differently across categories [category details uncertain].

### Audio Category Distribution and Mixture (proportions and control strategy for speech/sound-effect foley/music/ambient sound/silence) — a dimension unique to AV models ⚠️

This is a dimension unique to AV models; in this batch, ALIVE and NAVA have substantive designs, while the rest are comparatively weak:
【ALIVE — staged two-part speech/sound-effect design + active BGM proportion control】
(1) The two-stage proportion switch in the audio tower is very pronounced: T2A Stage I is pure speech pretraining, using 700k hours of transcribed speech (384M samples, 1 epoch, lr 5e-5), at which stage the data is almost entirely speech; T2A Stage II switches to a mixture — "approx. 5k hours" of high-quality speech plus "111k hours" of video data with sound annotations (19M samples, 10 epochs) — i.e., a drop from "700,000 hours of pure speech" down to "5,000 hours of curated speech" while heavily blending in native audio tracks from video. This is a clear scheduling pattern of "large-scale speech base → small-scale high-quality speech maintenance + large-scale real-soundscape supplementation." Note that the epoch count in Stage II (10) is far higher than in Stage I (1), indicating that the high-quality mixed data is reused repeatedly.
(2) Active BGM proportion control: original text: "we assess the correlation and separate samples where the audio is highly correlated with the visual content, while also managing the proportion of weakly correlated data, such as background music (BGM), to optimize the dataset's composition." — audio is split in two by "strength of correlation with the visual content": strongly correlated (diegetic, on-screen sound) samples are collected separately, while weakly correlated samples (such as BGM, non-diegetic) have their proportion controlled rather than being entirely removed. This is a more nuanced strategy than "blanket removal of BGM": retaining a certain proportion of weakly correlated audio lets the model learn to generate scoring music, but too high a proportion would break the audio-visual causal relationship. The specific proportion is not disclosed [uncertain].
(3) Three-way split at the caption level: the <W> tag marks speech (verbatim speech content), the <I> tag marks non-speech acoustic events, and the acoustic profiles field within Subjects constitutes a third track — together forming three annotation tracks for speech, sound effects, and timbre.
(4) Among the nine Level-1 domains, Home Sounds and Sound Effects correspond directly to non-speech audio categories, and every Level-3 visual tag is bound to an audio keyword — audio category proportions are embedded into, and jointly scheduled with, the overall domain-mixture system.
【NAVA — corpus organization driven by five audio tag classes】Uses the YAMNet audio classifier together with an omni-modal tagger to label all clips into five categories: single-speaker speech / multi-speaker speech / ambient sound / music / singing. This five-way split is finer than the common three-way "speech/sound-effect/music" split, in particular separating single-speaker from multi-speaker speech (corresponding to its multi-speaker timbre-control capability) and separating music from singing (singing carries both speech and musical attributes, so it reasonably forms its own category). The audio mixture during training is expressed through an "audio-only : audio-visual" ratio schedule: Stage 1 is 3:1 (audio-dominant, first training up strong audio-generation capability), Stage 2 flips to 1:2 (audio-visual-dominant). The absolute proportion of each audio category is not disclosed [uncertain].
【CCL】Audio pretraining introduces the two sound-effect/general-audio datasets WavCaps and VGGSound, while the joint-training data (OpenHumanVid + interviews/short dramas/films) is dominated by dialogue speech — forming a structure of "general audio pretraining + speech-dominated joint training." Proportions are not disclosed [uncertain].
【Baton】Among the data sources, AudioCaps and WavCaps provide general sound-effect/soundscape descriptions, while OpenHuman-Vid provides human voice; the mixture ratio is not disclosed [uncertain].
【OmniCustom】Audio is almost entirely single-person speech (a voice-timbre customization task), with no sound-effect/music dimension; audio is uniformly resampled to 16kHz. This is the work with the most singular audio category among the seven.
【StreamChar】Character speech is the overwhelmingly dominant subject, with Emilia being a pure-speech dataset; no sound-effect/music category design [uncertain].
【ITS-JAVG】No training data; but its verifier combination covers both audio semantics (ImageBind-TA, AVHScore) and synchronization (JavisScore); one of its evaluation base models, MMDisCo, is based on VGGSound (dominated by sound effects), while the other, JavisDiT, covers a broader range of categories.

### Narrative Structure Distribution (single-shot vs. multi-shot, average clip duration, shot-count distribution, whether native audio tracks are included) ⚠️

【Single-shot dominant; only StreamChar touches on long-horizon narrative】
(1) Single-shot short clips: OmniCustom (fixed 5-second single-person speech, single shot), CCL (352×640 short clips), Baton (short clips, 10 seconds for evaluation), NAVA (average 7 seconds, segmented via a Hadoop pipeline, presumably single-shot clips), and ALIVE (3–10 second clips, 5–10 second output) are all single-shot structures, with no shot-change or transition samples.
(2) Extraction of short clips from long sources: ALIVE's character-driven pipeline explicitly extracts N clips of "3–10 seconds" from "10–30-minute long videos" — i.e., long videos are treated as a "multi-shot material pool of the same identity," used to construct cross-clip identity pairs (cross-pair). This indirectly introduces a supervision signal for "cross-shot consistency of the same character," even though each individual training sample remains single-shot.
(3) The sole explorer of long-horizon narrative: StreamChar is the only work in this batch to directly address long-horizon temporal structure, but its solution is not to train on long-video data — quite the opposite, training data is restricted to within 20 seconds ("training data contains no videos/transcripts longer than 20 seconds"), and long-horizon capability is obtained entirely through inference-time chunk-autoregressive concatenation (each chunk 33 frames @24fps) plus two explicit anti-drift mechanisms: the progress-aware pointer (supervised with smooth L1 loss on ground-truth end indices derived from ASR timestamps, letting the model know how far along the transcript it has reached) and the persistent visual anchor / sink chunk (a persistent visual anchor suppressing identity drift). An ablation shows that removing the sink chunk worsens drift from 0.0067 to 0.0304 (a roughly 4.5× degradation), quantitatively proving the visual anchor's critical role in long-range consistency. Evaluation generates a continuous 5-minute stream (using randomly sampled transcripts of >300 words).
(4) Proportion with native audio tracks: all seven use paired data with native, synchronized audio tracks — ALIVE explicitly states "begins by filtering videos with audio from the raw data pool" (the very first step is filtering the raw pool for videos with audio tracks), OmniCustom's/StreamChar's upstream datasets are themselves audio-video pairs, and the same holds for NAVA's audio-video subset. None adopt a route of "strip the audio track first and dub it in afterward."
(5) Shot-count distribution, average shot count, and similar statistics are not disclosed by any of the seven [uncertain].

This batch of works is generally weak on the language dimension, a shared shortfall:
【ALIVE】The language distribution of the training data is not disclosed [uncertain]; only the evaluation section mentions that evaluation prompts cover "multiple languages (Chinese and English)" — given Bytedance's product positioning and the 700k-hour transcribed-speech corpus, a Chinese-and-English-dominant mix can be inferred but there is no direct evidence [uncertain]. In the caption, content inside the <W> tag is verbatim speech content, indicating the transcription preserves the original language.
【NAVA】The repository explicitly states "English speech generation supported," and notes "limited other languages' support" — i.e., English-dominant with weak multilingual capability. This is consistent with its data sources containing a large amount of TED-style speech videos (the vast majority of TED talks are in English). The language distribution of the 15M corpus is not disclosed [uncertain]. Architecturally, the ReDimNet speaker embedder is introduced for timbre control, decoupling timbre from language, but language coverage remains limited by the data.
【StreamChar】Uses Emilia for orchestrator speech pretraining (80k steps) — Emilia is itself a large-scale multilingual speech dataset (covering English/Chinese/German/French/Japanese/Korean), which in principle provides a foundation for multilingual capability, but the paper does not report multilingual evaluation, so actual coverage is uncertain [uncertain].
【OmniCustom】Uses GLM-ASR to generate transcriptions for each 5-second training audio clip ("we used GLM-ASR to generate transcriptions for each 5s training audio clip") — GLM-ASR is a model with a Chinese-language advantage, suggesting a fair proportion of Chinese in the corpus [inferred, uncertain]. The caption explicitly annotates an accent attribute (following the Ovi attribute set). The evaluation set controls gender at 1:1 but does not control language proportion.
【CCL / Baton】Language distribution not mentioned [uncertain]. CCL's in-house data (interviews, short dramas, films) is mixed with OpenHumanVid, and the language composition is unclear; CCL reports a WER metric, indicating it evaluated speech intelligibility, but the language is unspecified.
【ITS-JAVG】No training data; the evaluation benchmarks VGGSound and JavisBench-mini are predominantly English-language environments.
【Overall judgment】None of the seven give a quantitative language/accent distribution table, and none report per-language evaluation of multilingual lip-sync. OmniCustom is the only work to make accent an explicit annotation field, and NAVA is the only work to honestly state that "multilingual support is limited."

## Filtering Pipeline

### Overall Filtering Funnel Structure (number of filtering stages, their order) ⚠️

The complexity of the data pipelines across the seven varies enormously, forming a spectrum from "no pipeline" to a "six-stage industrial pipeline":

【ALIVE — a six-stage industrial-grade pipeline (the most complete in this batch)】
Pre-filter: first filter the raw data pool for "videos with audio" (videos with audio tracks); samples without an audio track are eliminated immediately.
Original text: "our pipeline begins by filtering videos with audio from the raw data pool and then proceeds through six core stages: video quality pre-processing, captioning, audio quality filtering, SubjectID correction, clarity filtering, and data balancing."
Stage 1, Video quality pre-processing: OCR measures the proportion of overlaid text and detects watermarks → a pretrained aesthetics model scores frame by frame → RAFT computes optical flow for motion analysis → a quality model classifies each sample as high-quality or as falling into one of 13 low-quality dimensions.
Stage 2, Captioning: a caption model trained through two rounds of SFT, plus manually annotated sub-motion-unit timestamps → produces a three-part structured caption (Subjects / Visual / Narration), with speech marked inline as <W> and non-speech acoustic events marked inline as <I>.
Stage 3, Audio quality filtering: an MLLM applies dual criteria — an audio-quality score (removing samples with significant background noise) + audio-visual correlation (separating strongly correlated samples and controlling the proportion of weakly correlated data such as BGM).
Stage 4, SubjectID correction (speaker-to-subject attribution correction, a five-step sub-pipeline, the most distinctive design in this batch): ① TS-TalkNet performs active speaker detection, generating a face-voice correspondence matrix; ② Qwen3-omni parses narration timestamps; ③ majority voting builds a "sentence → TrackID" mapping; ④ CLIP / ArcFace embeddings perform visual-semantic matching; ⑤ text is rewritten using the corrected labels. Videos that fail to meet a high-confidence threshold are filtered out, yielding a "simplified" but high-quality initial dataset. This stage addresses the problem of misattributed speech in multi-person scenes — "which line belongs to whom" — a problem that pure video models never encounter but that AV models must confront.
Stage 5, Clarity filtering: evaluation using six clarity-tier reference images (from blurry to sharp).
Stage 6, Data balancing: top-level speaking/non-speaking split → nine Level-1 domains under a three-tier tagging system → proportion adjustment for each category based on concept frequency and anticipated application scenarios.
There is also a parallel Character-driven data pipeline (cross-pair + in-pair augmentation, see synthetic_data_synthesis).

【NAVA — a large-scale multi-operator pipeline (both ends of the funnel disclosed)】
Original pool ≈ 20M audio clips + 100M video clips → final result about 15M clips.
① Large-scale segmentation via a Hadoop pipeline ("raw videos are first segmented at scale with a Hadoop-based pipeline")
② PaddleOCR performs OCR-based filtering and subtitle removal (note this is "removal," not merely "exclusion")
③ VideoCLIP extracts video embeddings + large-scale k-means clustering to remove redundant/near-duplicate clips
④ Multi-operator quality filtering: visual side (aesthetics / sharpness / brightness / motion score), audio side (AudioBox Aesthetic score), audio-visual alignment side (three alignment operators — SyncNet / SyncFormer / ImageBind)
⑤ VLM-based filtering and tagging, retaining clips of clear visual quality
⑥ YAMNet audio classification + an omni-modal tagger for five-class audio tagging
⑦ Captioning: Qwen3-VL generates video captions, Qwen3-Omni generates audio captions, then Gemini-3-Flash performs direct concatenation or rewriting/fusion; the high-quality subset switches to Gemini-3-Pro instead
⑧ Multi-operator collaborative filtering produces a 160K high-quality SFT subset

【OmniCustom — a lightweight three-rule pipeline】Starting from SpeakerVid-5M (5.2M clips / 8,000 hours): ① SyncNet dual threshold (|offset|≤3 and confidence>1.5); ② aesthetic score <0.3 removed; ③ duration <10 seconds removed → yields OmniCustom-1M (about 1M clips / 2,500 hours). Afterward: unify format (480p/24fps, audio 16kHz) → GLM-ASR transcription → reference-training pair splitting (first 4 seconds as reference audio, last 5 seconds as training audio-video) → randomly sample and crop face-containing frames as reference images.

【StreamChar — dataset combination, no self-built pipeline】Directly combines SpeakerVid-5M + TalkVid + OpenHumanVid, with the added constraint of "no videos/transcripts longer than 20 seconds"; ASR timestamps are used as supervision labels for the progress-aware pointer. No explicit description of quality/sync filtering [uncertain].

【CCL / Baton — only a source list, no pipeline disclosed】CCL is OpenHumanVid + in-house (interviews/short dramas/films) + WavCaps/VGGSound; Baton is OpenHuman-Vid + AudioCaps + WavCaps + internet videos. Neither describes any filtering, tagging, or deduplication step [uncertain].

【ITS-JAVG — moves the pipeline to inference time】No training-data pipeline, but its structure is isomorphic to a data-filtering pipeline: for each prompt, generate N candidates (5 for JavisDiT, 10 for MMDisCo) → score with a set of verifiers (VideoReward-TA / JavisScore / ImageBind-TA / AVHScore / VQAScore / ImageBind) → aggregate adaptively via ARW → select the best via EvoSearch evolutionary optimization. This can be understood as "moving the joint multi-scorer filtering from the training-data pipeline to after generation, before output."

### Quantitative Funnel Retention Rates (input/output volume at each filtering stage and final retention rate, e.g., Apollo 27%) ⚠️

Only two works in this batch give a computable retention rate; the rest are entirely blank:
【OmniCustom — the only precisely computable funnel】
- Input: SpeakerVid-5M, "more than 5.2 million video clips" / "8,000 hours"
- Output: OmniCustom-1M, "about 1 million single-person video clips" / "2,500 hours"
- Clip-level retention rate ≈ 1.0M / 5.2M ≈ 19.2%
- Hour-level retention rate = 2,500 / 8,000 = 31.25%
- The discrepancy between the two retention rates is worth noting: the hour-level retention rate is markedly higher than the clip-level retention rate, indicating that the retained clips are on average longer (retained clips average about 2500h/1M ≈ 9.0 seconds vs. the original 8000h/5.2M ≈ 5.5 seconds) — a direct consequence of the "remove videos <10 seconds" rule, which cuts hard on clip count but the clips it removes are all short ones.
- The individual pass rates of the three rules are not given separately [uncertain].
【NAVA — only the two ends of the funnel, no intermediate layers】
- Input: "approximately 20M audio clips and 100M video clips"
- Output: "around 15M clips for large-scale training"
- Counting by the video side, the retention rate is about 15M/100M = 15%; combined, it would be lower still. The input/output volumes and pass rates of each individual stage (OCR/dedup/quality/alignment) are not disclosed [uncertain].
- Secondary convergence: 15M → a 160K high-quality SFT subset, an SFT retention rate of about 1.07% (i.e., roughly ten in a thousand) — a highly informative figure, illustrating that there are two orders of magnitude of difference between "trainable" and "SFT-grade premium."
【ALIVE】Gives no retention rate or original pool size at all; the shrinking trend can only be inferred from stage sample counts: 11M (joint training) → 4.3M (balanced, only 39% retained after balancing) → 5M (SFT) → 0.7M (1080p high-clarity subset, 6.4% of 11M) → 0.8M (character pairing). The "11M → 4.3M balanced" step's 39% retention rate, caused by data balancing (domain-mixture adjustment), is the only proportion in this batch other than OmniCustom's that can be back-calculated [an inference, uncertain].
【Baton / CCL / StreamChar】No funnel information at all [uncertain]. CCL's 4M is the final usage volume; the original candidate pool is unknown.
【ITS-JAVG】At inference time, the "retention rate" concept corresponds to the Best-of-N selection rate: 1/5 = 20% for JavisDiT, 1/10 = 10% for MMDisCo — coincidentally in the same order of magnitude as the 10%–20% retention rates commonly seen in industrial data pipelines, hinting that "oversample then select the best" follows a similar economics on both the training side and the inference side.

### Shot-Segmentation Methods (PySceneDetect/proprietary models/shot-aware splitting) ⚠️

Disclosure is minimal, a shared weak point of this batch:
【NAVA — the only mention of segmentation engineering】"raw videos are first segmented at scale with a Hadoop-based pipeline" — a distributed Hadoop-based pipeline is used for large-scale segmentation. Notably, the paper only specifies the engineering framework (Hadoop) without naming the segmentation algorithm or tool (it does not say whether it is PySceneDetect, TransNetV2, or a proprietary shot-detection model) [uncertain]. This "infrastructure-only, algorithm-unstated" style of disclosure itself suggests that segmentation is treated as an already-solved engineering problem. The average clip after segmentation is about 7 seconds.
【ALIVE】There is no independent shot-segmentation stage among the six data-pipeline stages; the segmentation action is implicit within the character-driven pipeline: "Extracts N clips (3–10 seconds) from long videos (10–30 minutes)" — N clips of 3–10 seconds are extracted from 10–30-minute long videos, but the basis for extraction (whether based on shot boundaries, speaker activity, or randomness) is not stated [uncertain]. Given that its identity anchor is selected as the "1.5-second sub-clip with the highest sync score," extraction is very likely driven by sync score rather than shot boundaries [inference, uncertain].
【OmniCustom】Performs no segmentation — it directly uses the already-segmented clips from upstream SpeakerVid-5M, and only performs "removal of clips <10 seconds" filtering plus fixed-point cropping of "first 4 seconds / last 5 seconds." This is a typical case of "outsourcing segmentation to the upstream dataset."
【StreamChar】Likewise performs no segmentation, entirely reusing the existing segmentation granularity of the three datasets SpeakerVid-5M / TalkVid / OpenHumanVid, only applying a "≤20 second" length constraint.
【Baton / CCL】Segmentation method not mentioned [uncertain]. Both use already-segmented public datasets such as OpenHumanVid, plus a self-collected/in-house portion (Baton's internet videos, CCL's short dramas and films) — the latter would in principle require segmentation, but this is entirely undescribed in the papers [uncertain], a clear gap in CCL's data disclosure (film and short-drama content has the densest shot changes, and segmentation quality should have a significant impact on its results).
【ITS-JAVG】Not applicable.
【Overall judgment】In this batch of 2026 works, shot segmentation has become highly "infrastructure-ized" — either outsourced to public datasets, or only the engineering framework is mentioned without the algorithm. This contrasts with the 2024–2025 trend of papers commonly naming PySceneDetect/TransNetV2, reflecting that this step is no longer regarded as a technical contribution point.

### Quality Filtering (aesthetic scoring, clarity, OCR text filtering, letterbox/watermark/logo detection) ⚠️

【ALIVE — four operator classes + an original six-tier clarity system (the most systematic in this batch)】
(1) OCR text and watermark detection: original text, "We employ Optical Character Recognition (OCR) to measure the proportion of overlaid text and detect watermarks" — note that its approach is to "measure the proportion of overlaid text" rather than a simple binary judgment, indicating filtering by a threshold on the proportion of text-covered area (the threshold is not disclosed [uncertain]).
(2) Aesthetic scoring: "utilize a pre-trained aesthetics model for per-frame scoring" — scoring is done per-frame rather than on sampled frames, a relatively fine granularity. The specific model and threshold are not disclosed [uncertain].
(3) Motion analysis: RAFT computes optical flow (see motion_filtering).
(4) A 13-dimensional low-quality classifier: "a quality model ... is used to classify samples as either 'high-quality' or belonging to one of 13 distinct low-quality dimensions" — a multi-label classifier that subdivides low quality into 13 dimensions. This is far more refined than the common "single quality score + threshold" approach, and can support differentiated treatment by dimension (e.g., some dimensions may be fixable, others must be discarded). However, the paper never lists what these 13 dimensions actually are [uncertain], the most regrettable omission in the entire text.
(5) An independent clarity-filtering stage: evaluated using "reference images across six distinct clarity levels" (six clarity-tier reference images, from blurry to sharp) as the judgment benchmark — i.e., clarity is turned into a six-level ordinal label rather than a continuous score or binary judgment. The 0.7M "high-clarity samples" used specifically in the 1080p Refiner stage are filtered from the highest tier. This kind of "reference-image-anchored ordinal grading" is rarely seen in contemporaneous work; its advantage is high annotation consistency and cross-annotator comparability.
【NAVA — multi-operator parallelism + VLM re-filtering】
(1) PaddleOCR performs OCR filtering and subtitle removal — the distinctive part is that it does not merely "discard upon detecting subtitles" but performs "subtitle removal," repairing subtitled material and continuing to use it, significantly improving data utilization. This contrasts with ALIVE's approach of "measuring text proportion then filtering": one repairs, the other removes.
(2) A group of visual-quality operators running in parallel: aesthetics, sharpness, brightness, and motion score. All thresholds are undisclosed [uncertain].
(3) VLM-based filtering and tagging: a vision-language model performs a second-pass filter for "visually clear" clips — i.e., large-model semantic judgment is layered on top of traditional scorers (see model_as_data_judge for details).
【OmniCustom — a single aesthetic threshold (the only work in this batch to give a numeric aesthetic threshold)】Explicitly removes videos with "aesthetics scores below 0.3" — an aesthetic score <0.3 is eliminated. This is the only publicly disclosed aesthetic-threshold number in this batch, although its score scale (0–1 normalized) and the specific aesthetic model are not stated [uncertain]. There is also removal for duration <10 seconds. No description of OCR / watermark / resolution filtering [uncertain].
【StreamChar / CCL / Baton】No visual quality filtering described at all [uncertain]. All three rely on the quality filtering already built into their upstream public datasets (OpenHumanVid, SpeakerVid-5M, and TalkVid all carry their own quality filters), a form of "outsourced quality control."
【ITS-JAVG (quality gatekeeping at inference time)】In its verifier combination, VQAScore and VideoReward-TA are responsible for gatekeeping visual quality and text consistency, which can be seen as "inference-time quality filtering." The paper's key finding is that any single quality verifier is exploited by the search algorithm ("the inference-time search algorithm exploits blind spots"), requiring a combination of multiple verifiers — a conclusion that also serves as a warning for training-side data filtering: using a single aesthetic score or a single quality model as the sole filtering criterion likewise leaves a blind spot that can be "exploited in reverse" by the data distribution.

### Motion Filtering (optical flow/motion score thresholds, removal of static and jittery content) ⚠️

Disclosure is sparse, involving only two works:
【ALIVE】Uses RAFT to compute optical flow for motion analysis — original text: "compute optical flow using RAFT." RAFT is the only optical-flow model named in this batch, consistent with the choice made by earlier works such as Ovi and HunyuanVideo, indicating RAFT has become the de facto standard for this step. However, ALIVE does not state: the motion-score threshold, whether static clips are removed, whether overly jittery/high-motion clips are removed, or whether the motion score serves as a downstream condition or curriculum-scheduling basis [all uncertain].
【NAVA】Lists motion score as one of its visual-quality operators, alongside aesthetics / sharpness / brightness. The computation method (whether based on optical flow, and which model) and the threshold are not stated [uncertain].
【OmniCustom】No motion filtering — reasonable, since its data is entirely single-person talking heads, where motion amplitude is naturally small and concentrated on the face; applying motion filtering would instead risk removing valid samples. This suggests the necessity of motion filtering is strongly domain-dependent: general-purpose video generation must do it, talking-head customization can skip it.
【StreamChar / CCL / Baton】Not mentioned [uncertain].
【ITS-JAVG】Does not involve training-side motion filtering, but VideoReward-TA among its verifiers implicitly evaluates motion quality.
【Overall judgment】Compared to 2024–2025 papers, which commonly detailed motion-score thresholds and dual-ended removal of static/jittery content, this batch of 2026 works spends noticeably less ink on motion filtering — even thresholds are no longer mentioned — reflecting that this step is now regarded as a standardized "known operation," with the technical narrative's focus having shifted to audio-video alignment and semantic tagging.

### Deduplication Methods (exact deduplication and embedding-based semantic deduplication recorded separately) ⚠️

【NAVA — the only work to perform semantic deduplication with a clearly stated method】Original text: "Redundant or near-duplicate clips by extracting video embeddings with VideoCLIP and performing large-scale k-means clustering" — video embeddings are extracted with VideoCLIP, followed by large-scale k-means clustering, on the basis of which redundant and near-duplicate clips are removed. This is typical embedding-based semantic deduplication (rather than hash-level exact deduplication); the k value, the intra-cluster retention strategy (how many clips retained per cluster, by what ranking), and the similarity threshold are all undisclosed [uncertain]. Choosing VideoCLIP over per-frame CLIP suggests temporal considerations were also factored in. No mention of exact deduplication (pHash/frame fingerprinting/file hashing) [uncertain].
【ALIVE】There is no deduplication step at all among the six pipeline stages; the paper never mentions deduplication [uncertain]. Given that its data source is an internal raw data pool at a scale of 11M samples, the absence of deduplication is a notable gap — unless its original pool had already been deduplicated before ingestion (not stated in the paper).
【OmniCustom / StreamChar】Rely on the deduplication already built into upstream datasets (SpeakerVid-5M / TalkVid / OpenHumanVid), with no deduplication step of their own [uncertain]. OmniCustom carries an implicit "anti-deduplication" risk: its construction of "first 4 seconds as reference + last 5 seconds as training" pairs from the same long video means the same speaker may appear repeatedly multiple times in the dataset — a feature rather than a defect for an identity-customization task (which needs multiple samples of the same identity), but it also means the speaker-level distribution may be highly imbalanced [uncertain].
【CCL / Baton】Deduplication not mentioned [uncertain]. Baton mixes four sources — OpenHuman-Vid, AudioCaps, WavCaps, and internet videos — AudioCaps is itself a subset of AudioSet, and part of WavCaps also overlaps with AudioSet/FreeSound, so cross-dataset duplication risk objectively exists but is not addressed in the paper [uncertain].
【ITS-JAVG】Not applicable; but the candidate-diversity-maintenance problem within its Best-of-N / EvoSearch is mathematically homologous to the "sample redundancy" problem that deduplication addresses.
【Overall judgment】Only NAVA among the seven performs explicit deduplication, and it is also the work with the most complete data disclosure in this batch — corroborating a general pattern: investment in deduplication correlates with data scale (NAVA processes 100M videos, while the rest mostly operate at the 1M–11M scale or directly reuse already-cleaned public datasets).

### VLM/LLM as Quality Inspectors (multimodal large-model quality scoring and mismatch removal; the 2026 trend of shifting from shallow scorers to large-model semantic judgment) ⚠️

This dimension best embodies the 2026 trend in this batch of works — both ALIVE and NAVA embed MLLMs/VLMs deeply into their data pipelines, using them not only for tagging but directly for quality-inspection and semantic-judgment duties:
【ALIVE — MLLM for audio quality inspection and speaker-attribution correction (the deepest application in this batch)】
(1) MLLM performs dual-criteria audio quality inspection: original text, "We utilize an MLLM model ... to perform audio filtering based on two criteria. Firstly, for audio quality, the model assigns a score to each audio, allowing us to discard samples with significant background noise. Secondly, for audio-visual coherence, we assess the correlation ..." — i.e., a multimodal large model simultaneously handles two tasks: scoring audio quality (removing samples with significant background noise), and judging audio-visual semantic correlation (separating strongly correlated samples, controlling the proportion of weakly correlated samples such as BGM). This marks a signature shift: audio-quality filtering traditionally relies on signal-processing metrics like SNR and silence detection, but ALIVE instead has a large model directly "listen" and score; audio-visual correlation traditionally relies on contrastive-learning models such as CLAP/ImageBind to compute similarity, but ALIVE instead uses a large model for semantic judgment.
(2) Qwen3-omni parses narration timestamps: in the SubjectID correction pipeline, Qwen3-omni (an omni-modal large model) is used to parse the timestamps of narration — treating an omni-modal LLM as a temporal-alignment annotator.
(3) Gemini 2.5 participates in other parts of the pipeline (mentioned in the paper but its role is not fully clear [uncertain]).
(4) Traditional scorers are still used in parallel: OCR, a pretrained aesthetics model, RAFT, TS-TalkNet, CLIP, ArcFace, the 13-dimensional quality classifier — forming a hybrid system of "large-model semantic judgment + dedicated scorers," rather than complete replacement.
【NAVA — VLM filtering + a three-model division of labor across Gemini/Qwen for tagging】
(1) VLM-based filtering and tagging: a vision-language model filters and tags clips of clear visual quality — an explicit case of "VLM as quality inspector."
(2) An omni-modal tagger paired with YAMNet for five-class audio classification — a traditional audio classifier (YAMNet) works together with an omni-modal large-model annotator, the former providing fast coarse classification, the latter providing semantic refinement.
(3) A three-model division of labor for tagging: Qwen3-VL (video captions), Qwen3-Omni (audio captions), Gemini-3-Flash (fusion/rewriting); the high-quality subset is upgraded to Gemini-3-Pro. Using models of different price tiers to process data of different quality tiers is a classic cost-quality engineering trade-off.
(4) "Multi-operator collaborative filtering" produces a 160K SFT subset — the word "collaborative" implies each operator's scores are jointly combined rather than serially thresholded [the specific aggregation method is uncertain].
【OmniCustom】Uses GLM-ASR for transcription, a dedicated model rather than a general-purpose MLLM; the caption construction follows the Ovi attribute system (speaker age, gender, accent, pitch, prosody, emotion, speaking rate), and does not state which model was used to generate these attribute annotations [uncertain], nor does it use a large model for quality inspection. Filtering relies entirely on the three hard rules of SyncNet + aesthetic score + duration.
【CCL / Baton / StreamChar】None use a large model for data quality inspection [uncertain]. Although Baton has Qwen3-8B as the VA-Planner backbone, that is a model-architecture component rather than a data-pipeline role.
【ITS-JAVG — formalizing the "model as judge" paradigm and demonstrating its pitfalls (the most theoretically valuable contribution to this dimension)】
Although it does not involve training data, its core research object is precisely the "model as judge" paradigm itself, and its conclusions transfer directly to data quality inspection:
(1) Six verifiers each with their own duty: VideoReward-TA (text-video consistency), JavisScore (fine-grained audio-video synchronization), ImageBind-TA (semantic coherence between text and generated audio), AVHScore (semantic consistency between audio events and visual events), VQAScore (text-video alignment), ImageBind (audio-video semantic similarity).
(2) Core finding one: a single verifier inevitably leads to asymmetric trade-offs — "single-verifier guidance effectively improves its intended evaluation metrics, yet fails to achieve a balanced improvement across all metrics," meaning optimizing for one judge's score sacrifices other dimensions.
(3) Core finding two: verifier hacking genuinely exists — the search algorithm will "exploit blind spots" (exploit the judge's blind spots). This is an important warning for training-side data filtering: if a single model scorer is used for strict filtering, the retained data will be systematically biased toward that scorer's preferences and blind spots, creating a hidden distortion of the data distribution.
(4) The ARW solution: treats reward aggregation as an online optimization problem, with the formula R(i)=Σ_k w_k · r_k(i)/(σ_k+ε) (weighting each judge's score after normalizing by its standard deviation), optimizing the objective L_ARW=Σ_k (½exp(−s_k)·Var̂(r_k) + ½|s_k|) — i.e., adaptively adjusting weights according to the variance of each judge's scores, giving higher weight to judges with higher variance (higher discriminative power). This methodology of "adaptive normalized aggregation of multiple judges' scores" could readily be transplanted onto multi-operator collaborative filtering of training data (coincidentally, NAVA's own "multi-operator collaborative filtering" does exactly this, but without disclosing its aggregation algorithm).

## Annotation and Captioning

### Caption Models Used (self-developed VLM/open-source model, model scale) ⚠️

This batch of works shows a clear evolution in caption models, from "dedicated small models" → "general-purpose large models" → "multi-model division of labor":
【ALIVE — a self-trained caption model + two rounds of SFT + manual revision (a self-built route)】
(1) The visual caption model went through two rounds of supervised fine-tuning (two-round SFT), with the training data being MLLM-generated captions that were then "manually revised caption data" — i.e., the classic self-built path of "large model generates → human revises → distilled via SFT into a dedicated caption model," trading a one-time human cost for low-cost large-scale inference.
(2) A second type of manual annotation: "decomposing sub-motion units to annotate the start and end timestamps of each complete small action" — actions are decomposed into sub-motion units, and humans annotate the start and end timestamps of each complete small action. This is an extremely high-cost fine-grained temporal annotation, aimed at giving the caption precise timeline information (serving the temporal narration of the Narration field and the temporal alignment of UniTemp-RoPE).
(3) Audio-information fusion: an MLLM processes the visual description to "incorporate the relevant audio information," achieving audio-visual convergence. The paper does not consistently name the base model of the main caption model [uncertain]; Gemini 2.5 and Qwen3-omni appear elsewhere in the pipeline.
【NAVA — three-model division of labor + a two-tier strategy (an external-large-model route)】
(1) For the full dataset: Qwen3-VL generates video captions, Qwen3-Omni generates audio captions, and the two "are then fused by either direct concatenation or rewriting by Gemini-3-Flash" — Gemini-3-Flash performs the fusion, either by direct concatenation or by rewriting. Note the "direct concatenation or rewriting" either/or, indicating a cost-tier split: some data receives only concatenation (zero cost), some receives rewriting (with a cost).
(2) For the high-quality subset: upgraded to Gemini-3-Pro, "to produce more accurate, structured, and temporally grounded audio-visual captions." "Temporally grounded" is the key term here, echoing ALIVE's sub-motion timestamp annotation, indicating that the competitive focus of 2026 AV captioning has shifted to temporal precision.
(3) This "Flash for the full dataset + Pro for the premium subset" two-tier strategy is the clearest caption cost-engineering practice in this batch.
【OmniCustom】Uses GLM-ASR to generate transcriptions for each 5-second training audio clip; the audio caption's attribute system explicitly states "Following the OVI model approach," emphasizing the speaker's age, gender, accent, and vocal characteristics (pitch, prosody, emotion, speaking rate). The model used to generate these attribute annotations is not stated [uncertain]. Whether the visual caption is self-built is not stated [uncertain].
【StreamChar】Uses ASR timestamps ("ground-truth end indices derived from ASR timestamps") as the supervision signal for the progress-aware pointer, but does not name the ASR tool [uncertain]; visual captions rely on annotations already provided by the upstream datasets [uncertain].
【CCL / Baton】No description at all of a caption model or tagging process [uncertain]. Although Baton uses Qwen3-8B as the VA-Planner backbone and regresses to SigLip2 / WavTokenizer features, this is an architectural component, not a data-annotation step; its training data's captions come from the native annotations of OpenHuman-Vid / AudioCaps / WavCaps, and how the internet self-collected portion is tagged is not stated [uncertain].
【Overall pattern】The larger the data volume, the more likely a work is to build its own caption model (ALIVE, 11M samples → self-trained + manual revision); medium-scale works tend to call external large models (NAVA, 15M but using a Qwen3/Gemini combination, tiered to control cost); small-scale works directly reuse upstream annotations (Baton 1.5M, CCL 4M).

### Caption Density and Structuring (short/long/dense descriptions, structured fields such as camera motion, style tags) ⚠️

【ALIVE — three-part structuring + inline temporal tags (the most refined in this batch)】
The caption schema explicitly splits into three fields:
- Subjects: containing "visual appearance + acoustic profiles" — i.e., every subject carries both a visual-appearance description and an acoustic profile at the same time. Binding "what this person looks like" together with "what this person sounds like" under the same subject entry is a key innovation in AV-model caption design: it lets the model unify the visual and auditory sides of identity during generation (and is also why the SubjectID correction stage requires a costly five-step sub-pipeline to correct speaker attribution — if attribution is wrong, the acoustic profile gets attached to the wrong face).
- Visual: visual context, i.e., scene setting.
- Narration: the temporal sequence of actions, embedding two types of special tokens:
  · <W>: wraps verbatim speech content
  · <I>: marks non-speech acoustic events
That is, visual action narration, dialogue, and sound effects are all interwoven in temporal order within the same Narration track. This is similar in spirit to, but more thorough than, Ovi's <S>...<E> + <AUDCAP> scheme — Ovi places the audio description uniformly at the end, whereas ALIVE also pulls the non-speech events <I> inline onto the timeline, giving stronger temporal expressiveness.
Paired with manually annotated sub-motion-unit start/end timestamps, the Narration's temporal precision has ground-truth support.
【NAVA — a unified-template, structured, dense caption (four major sections)】
Explicitly adopts "structured dense captions rather than free-form short descriptions," with a unified template covering four sections:
- Global visual semantics: style, mood, subject, appearance, background, lighting
- Temporal dynamics: initial state, action sequences, motion details, ending state — an explicit "initial state → process → end state" three-part temporal skeleton
- Camera behavior: camera angle, shot scale, framing, composition
- Audio description: four categories — speech, SFX, music, ambient sound
Roughly 18 explicit fields in total, the most complete caption schema in this batch. It is particularly notable that it singles out "camera behavior" as its own section (4 fields), which is uncommon in AV generation work, indicating that NAVA has a clear demand for camera controllability.
【OmniCustom】The audio caption follows the Ovi system: speaker age, gender, accent + vocal characteristics (pitch, prosody, emotion, speaking rate), 7 attributes in total; plus per-segment transcription produced by GLM-ASR. The structure of the visual caption is not described [uncertain]. This is a design that is "structured on the audio side, unspecified on the visual side," consistent with its narrow identity+timbre customization task.
【Baton — no text captions, using continuous features as a "semantic blueprint" (the most unconventional in this batch)】
Baton's core argument is precisely that "text captions are not enough": existing methods rely on coarse-grained embeddings from off-the-shelf text encoders, which "discards fine-grained semantics" and lack shared long-horizon planning. Its alternative is to have the VA-Planner (Qwen3-8B backbone) produce planned tokens, and via dual semantic alignment towers (each equipped with learnable queries for cross-modal attention) project the planned tokens into the continuous feature space of pretrained perceptual encoders — aligning on the video side to the penultimate-layer features of a frozen SigLip2, and on the audio side to the penultimate-layer features of a frozen WavTokenizer, supervised with L2 regression. The paper explicitly explains why discrete tokens are not used: "regressing continuous features preserves richer semantic structure."
This represents a new direction in the caption-structure spectrum: shifting from "ever-more-structured text captions" toward "bypassing text and using continuous perceptual features directly as the cross-modal semantic intermediary." If this route proves valid, future AV data pipelines may shift their focus from "how to write good captions" toward "how to choose good perceptual encoders."
【CCL / StreamChar / ITS-JAVG】Caption structure not described [uncertain]. StreamChar uses a transcript (the full dialogue text) rather than a descriptive caption, with the orchestrator's input being "the transcript and historical context" — a "script-driven" rather than "description-driven" conditioning form.

### Joint Audio-Video Caption Structure (whether visual and auditory tracks are jointly covered, whether they are split into independent fields — e.g., LTX-2's full soundscape description, Script-a-Video's factorized streams, Foley-Omni's three-field split) ⚠️

This batch of works diverges into four paradigms on joint audio-video captioning, making this the most informative cross-section of the 2026 landscape on this dimension:
【Paradigm 1｜Interleaved inline (ALIVE)】Three fields + dual tags: Subjects[visual appearance + acoustic profile] / Visual[scene] / Narration[action timeline + <W> verbatim dialogue + <I> non-speech acoustic events]. All three tracks (visual action, speech, sound effects) are entirely interleaved inline within the same temporal narrative, distinguished by tags rather than by field. Compared with Ovi's "<S>dialogue<E> inline + <AUDCAP> soundscape block appended at the end," ALIVE also pulls <I> (non-speech events) inline onto the timeline, giving more thorough temporal expressiveness. Another distinctive point is that the Subjects field binds "visual appearance" together with the "acoustic profile" under the same subject — this elevates audio-visual alignment from the "temporal level" to the "entity level," and is also the fundamental reason it must use a five-step SubjectID correction pipeline to guarantee correct attribution.
【Paradigm 2｜Split fields side by side (NAVA)】Under a unified template, audio functions as an independent section standing alongside the visual section, with the audio section further subdivided into speech / SFX / music / ambient sound. The production method is "two models produce separately + a third model fuses": Qwen3-VL produces the video caption, Qwen3-Omni produces the audio caption, and Gemini-3-Flash (or Pro) performs the concatenation or rewriting/fusion. This "split-then-merge" production method corroborates the final "split-fields-side-by-side" structure, but it also brings a latent risk: the two models, generating independently, could produce mutually contradictory audio and visual descriptions, and the fusion model would need to bear the responsibility of consistency checking (the paper does not state whether such a check exists [uncertain]).
【Paradigm 3｜Attribute-based audio captioning (OmniCustom)】Explicitly constructs its audio caption "Following the OVI model approach," emphasizing "speaker's age, gender, accent, and vocal characteristics (e.g., pitch, prosody, emotion, and speaking rate)" — i.e., the audio caption does not describe "what was heard" but rather "what kind of person the speaker is," a speaker-attribute-based schema. Combined with the per-segment transcription from GLM-ASR, this forms a two-track structure of "attribute description + dialogue content." This schema directly serves its timbre-customization task: controllable attributes = controllable timbre.
【Paradigm 4｜Bypassing text captions (Baton)】Does not construct a joint caption at all; instead uses planned tokens output by the VA-Planner as a shared audio-video semantic blueprint, with the video side and audio side each aligned via dual semantic alignment towers to the continuous feature spaces of SigLip2 and WavTokenizer respectively. This is a negation of the "joint caption" paradigm itself — its argument is that text embeddings inherently lose fine-grained semantics, and using continuous perceptual features as the cross-modal intermediary carries more information. RS-RoPE (Relative Semantic RoPE) is responsible for injecting the blueprint into the denoising process.
【No schema｜CCL / StreamChar / ITS-JAVG】CCL does not describe a joint-caption design [uncertain]; StreamChar uses a transcript (the dialogue text) rather than a descriptive caption as its primary condition, a "script-driven" rather than "description-driven" paradigm; ITS-JAVG has no training data, but its verifier AVHScore precisely measures "semantic consistency between audio events and visual events" at inference time — equivalent to replacing the audio-visual semantic-binding relationship that a joint caption would want to encode with a discriminative model checking it at the output end instead.
【Positioning relative to prior work】Placing this batch into the larger picture: Ovi represents "inline tags + a trailing soundscape block," LTX-2 represents "a unified full-soundscape description," Script-a-Video represents "fully factorized independent streams," and Foley-Omni represents "a three-field split." ALIVE is a reinforced version of the Ovi route (more thorough inlining + entity-level binding), NAVA follows the factorized route (fields laid out side by side), OmniCustom follows the attribute-based dedicated route, and Baton opens up a fourth path of "non-text intermediation." The state of play in H1 2026 is that the two mainstream approaches — inline temporal interleaving and split-field structuring — run in parallel, while an exploration of bypassing text altogether has also emerged.

### Dialogue Transcription and Speaker-Attribute Annotation (ASR transcription + speaker identity/language/accent/emotion) ⚠️

【OmniCustom — the most complete (dialogue transcription + seven speaker attributes)】
(1) Transcription: "we used GLM-ASR to generate transcriptions for each 5s training audio clip" — GLM-ASR generates a transcription for each 5-second training audio clip. GLM-ASR is a Zhipu-affiliated speech-recognition model with relatively strong Chinese-language capability.
(2) Speaker attributes (following the Ovi system): age, gender, accent + four vocal-characteristics attributes (pitch, prosody, emotion, speaking rate), 7 attributes in total.
(3) Implicit timbre annotation: its "same timbre, different content" pairing construction (the first 4-second reference audio and the last 5-second training audio coming from the same video and the same speaker) essentially provides timbre supervision without any explicit voiceprint annotation — within the same pair, timbre stays constant while content differs, naturally forming a contrastive-learning signal for timbre disentanglement. This is far cheaper than explicit voiceprint-ID annotation, and is a very clever piece of data construction.
(4) The evaluation set controls the gender ratio at 1:1, and includes 30 real people outside the training set to verify zero-shot timbre transfer.
【ALIVE — speaker-attribution correction is its unique contribution】
(1) Transcription annotation: the <W> tag wraps verbatim speech content, indicating precise ASR transcription exists; the <I> tag marks non-speech acoustic events.
(2) Acoustic profiles: every subject in the Subjects field carries acoustic profiles, i.e., speaker timbre attributes bound to visual appearance.
(3) The SubjectID correction five-step pipeline (targeting the misattribution problem of "who is speaking" in multi-person scenes, the only work in this batch to systematically address it):
  ① TS-TalkNet performs target-speaker active-speaker detection, generating a face-voice correspondence matrix
  ② Qwen3-omni parses the timestamps of the narration
  ③ Majority voting establishes a "sentence → TrackID (face-track ID)" mapping
  ④ CLIP + ArcFace embeddings perform visual-semantic matching
  ⑤ Text is rewritten using the corrected labels
Videos that fail to meet the high-confidence threshold are directly filtered out, yielding a "simplified" but high-quality initial dataset. This pipeline addresses a problem that pure video models never encounter at all: attaching dialogue to the wrong face in a multi-person scene, which would teach the model a wrong "face-voice" binding, directly undermining lip-sync and timbre consistency in multi-person conversation scenes. The specific threshold value is not disclosed [uncertain].
【StreamChar】Uses ASR timestamps as supervision: "ground-truth end indices derived from ASR timestamps," used for the progress-aware pointer's smooth L1 loss — i.e., "how far along in the transcript" progress information is used as an explicit supervision signal, forming the data foundation of transcript fidelity. The ASR tool is not named [uncertain]; speaker-attribute annotation is not described [uncertain].
【NAVA】Timbre-in-Context Conditioning encodes a "reference utterance" via a timbre encoder (implemented as the ReDimNet speaker embedder) and associates the reference-timbre cue with the corresponding speech spans — i.e., timbre is not a global condition but is bound per speech segment, supporting distinct timbres for multiple speakers. However, the paper does not state the annotation protocol (how speech-span boundaries are determined, whether diarization is used) [uncertain]; the ASR method is not detailed [uncertain]. Its five-class YAMNet labels distinguish single-speaker / multi-speaker speech, which can be viewed as a coarse-grained speaker-count annotation.
【CCL】Reports a WER metric, indicating that speech intelligibility was evaluated, implying a transcription-vs-generation comparison exists, but the data-side transcription process is not described [uncertain].
【Baton】Not described [uncertain].

### Geometric and Structured Annotation (camera parameters, depth, 3D point tracks, action annotation, explicit state) ⚠️

This batch of works is generally weak on geometric annotation, with the only bright spot being face/identity-related structured annotation (which matters more to AV models than camera parameters):
【ALIVE — structured face-track and identity annotation (the only work with substantive structured annotation in this batch)】
(1) Face-track ID (TrackID): the SubjectID correction pipeline builds a "sentence → TrackID" mapping, indicating the data contains face-track-level structured annotation (each face is tracked over time and assigned an ID).
(2) Face-voice correspondence matrix: the face-voice correspondence matrix produced by TS-TalkNet is an explicit structured cross-modal association annotation.
(3) Identity embeddings: ArcFace facial embeddings + CLIP visual embeddings, used for cross-clip identity matching. The character-driven pipeline gives explicit matching thresholds: face similarity >0.35, CLIP similarity >0.7, absolute proximity to 0.9 — the only set of publicly disclosed identity-matching thresholds in this batch.
(4) Sync score: TS-TalkNet's sync score is used to select the identity anchor ("1.5-second sub-clip with maximum sync score").
(5) Manual sub-motion-unit timestamp annotation: actions are decomposed into sub-motion units and humans annotate their start/end times — a form of temporal structured annotation (action boundaries), which, while not geometric, is explicitly structured.
(6) Not covered: camera intrinsics/extrinsics, depth maps, 3D point tracks, pose keypoints, segmentation masks [all uncertain].
【NAVA】The caption template's "camera behavior" section (camera angle, shot scale, framing, composition) — this is a language-based description of the camera rather than numeric camera parameters, a form of "weak structuring." No depth, 3D track, pose, etc. [uncertain]. The speaker embedding (ReDimNet) can be viewed as structured annotation on the acoustic side.
【OmniCustom】The reference image is obtained by "randomly sampling and cropping a frame containing a face" — implying face-detection annotation exists, but it is used only for cropping and not preserved as a structured field [uncertain]. No geometric annotation.
【StreamChar】Uses a reference frame and a motion frame as conditions — the motion frame is an implicit representation of motion state, not explicit geometric annotation. ASR timestamps are a form of temporal structured annotation.
【Baton】The planned tokens are essentially "continuous semantic features," which can be seen as another form of non-human-readable implicit structured intermediate representation — an alternative to traditional structured annotation: rather than annotating human-defined structures (camera, depth, action), it lets the model learn its own semantic structure. The penultimate-layer features of SigLip2 and WavTokenizer are the carriers of this "structure."
【CCL / ITS-JAVG】None [uncertain].
【Overall judgment】The focus of "structured annotation" for AV generation models is clearly different from that of pure video generation models: the latter cares about camera parameters, depth, and 3D trajectories, whereas the former cares about face-track IDs, face-voice correspondence, speaker embeddings, and speech timestamps. ALIVE's face-voice correspondence matrix and TrackID system are the most typical embodiment of this difference.

### Synthetic Data Construction (controlled perturbation/editing to construct training pairs, e.g., InstructAV2AV) ⚠️

【ALIVE — the only work in this batch to systematically construct synthetic/augmented data, and its method is worth a close look】
The Character-driven data pipeline has two branches:
(1) Cross-pair Pipeline (cross-clip pairing, constructing "same identity, different scene" training pairs from real data):
  - Extract N clips of "3–10 seconds" from 10–30-minute long videos
  - Select the "1.5-second sub-clip with maximum sync score" as the identity anchor — choosing the anchor by sync score rather than image-quality score is deliberate: a high sync score means the person is clearly speaking and facing the camera at that moment, the instant when identity features are most fully exposed
  - Use CLIP + ArcFace embeddings for multi-subject feature matching
  - A valid cross-clip pair must simultaneously satisfy: face similarity >0.35, CLIP similarity >0.7, absolute proximity to 0.9
  This branch is "mining same-identity pairs from real long videos" — it does not generate synthetic pixels, but it is a typical case of training-pair construction.
(2) In-pair Augmentation (within-clip augmentation, genuine synthetic-data construction):
  - Pose/expression perturbation
  - Background augmentation/replacement
  - Semantic editing via Qwen-Image-Edit
  The purpose is explicit: "to decouple identity from appearance" — i.e., teaching the model that "this person, with a different pose, a different background, different clothing, is still the same person," rather than treating background and clothing as part of the identity itself. Using an image-editing large model for controlled perturbation to construct positive pairs is a very typical practice in 2026 (sharing the same lineage as InstructAV2AV-style approaches, but ALIVE applies it to identity decoupling rather than instruction editing).
(3) Synthetic construction on the prompt side: during training, cross-attention signal dropout is applied with a 0.3 probability, a form of conditional-dropout augmentation; at inference time, a dense vector index is built with FAISS to extract sound events from the user's prompt and retrieve nearest neighbors, with a similarity threshold of τ>0.85, for retrieval-augmented prompt rewriting — this is synthesis at inference time rather than training time.
【OmniCustom — pair construction rather than pixel synthesis】Its "first 4 seconds as reference audio / last 5 seconds as training audio-video" splitting strategy is a zero-cost method of pair construction: "each reference-training pair shares the same timbre but contains distinct speech content" (same timbre, different content). This directly provides supervision for timbre disentanglement: the model must learn to extract only timbre from the reference audio without copying its content. The reference image is likewise randomly sampled and cropped from face-containing frames, also a form of pair construction. No pixel-level synthesis or editing.
【StreamChar — distillation data as self-generated data】In the two-stage distillation, Stage II is "rollout consistency" (fine-tuning the student under online chunk rollout), which essentially uses the student model's own generated rollout sequences as training data — an on-policy self-generated form of data, different from traditional synthetic-data construction but belonging to the same broader category of "model output fed back into training." Stage I compresses to a 4-step generator over 600 steps; Stage II runs 400 steps, with student lr 2e-6 and fake-score-network lr 4e-7. The distillation data source reuses the same set of audio-video datasets, with no additional construction.
【NAVA / CCL / Baton】No synthetic-data construction described [uncertain]. In Baton's three-stage training, the transition from Stage 2 to Stage 3 involves "switching from clean ground-truth features to the planner's predicted features," a form of curriculum-style input perturbation (replacing clean labels with the model's own imperfect predictions), conceptually close to scheduled sampling; it can be viewed as a form of synthesis on the training-input side, though it does not produce new data samples.
【ITS-JAVG】Its Best-of-N and EvoSearch generate large numbers of candidates at inference time and select the best — feeding the selected results back into training would constitute a synthetic-data pipeline, but the paper is explicitly training-free and does not pursue this extension. This is an obvious follow-up direction (using ITS's multi-verifier selection to produce high-quality synthetic SFT data), not addressed in the paper.

### Degree of Human Involvement (manual annotation, manual quality inspection, model pre-screening + manual review) ⚠️

The degree of human involvement varies markedly across this batch, with ALIVE being the only work with substantial manual-annotation investment:
【ALIVE — two types of manual annotation + manual evaluation (the heaviest investment in this batch)】
(1) Manually revised captions: the SFT training data for the caption model is "manually revised caption data," used across two rounds of SFT. This is the standard paradigm of "large model produces an initial pass + human review and revision + distillation into a dedicated model," a one-time human cost with returns that scale.
(2) Manual annotation of sub-motion-unit timestamps: "decomposing sub-motion units to annotate the start and end timestamps of each complete small action" — actions are decomposed into sub-motion units, with humans annotating the start and end timestamps of each complete small action. This is the most costly annotation item in this batch (unit cost for fine-grained temporal annotation is far higher than for descriptive labels), indicating the team places a high priority on temporal precision.
(3) The scale of both annotation types (number of items annotated, number of annotators, cost) is not quantified [uncertain].
(4) Manual evaluation: blind side-by-side comparisons against Veo 3.1, Kling 2.6, Wan 2.6, Sora 2, and LTX-2; Alive-Bench 1.0's 264 general prompts + 90 reference-character prompts and 22 fine-grained metrics (across six major categories) presumably involve manual design and judgment components [judgment-method details uncertain].
【StreamChar — explicitly quantified manual evaluation】"24 participants, each presented with 50 randomly sampled cases" — 24 participants, each evaluating 50 randomly sampled cases. This is the only work in this batch to give the number of human-evaluation participants and sample count. No manual annotation on the data side [uncertain].
【OmniCustom】The data pipeline is fully automatic (SyncNet + aesthetic score + duration, three rules, plus GLM-ASR), with no manual annotation step. There is human involvement in building the evaluation set: 100 carefully selected examples (30 real people outside the training set + 70 YouTube video segments), with the gender ratio controlled at 1:1 — this 1:1 ratio must be the result of manual curation.
【NAVA】The data pipeline is highly automated (relying entirely on OCR / VideoCLIP / various scorers / VLM / LLM), with no manual-annotation description [uncertain]. The 160K high-quality SFT subset is automatically selected by "multi-operator collaborative filtering" rather than manually curated. Evaluation includes user studies assessing four dimensions — video quality, audio-video synchronization, audio fidelity, and timbre controllability — but the scale of participants is not stated [uncertain].
【CCL / Baton】No description of human involvement [uncertain].
【ITS-JAVG】No training data, hence no annotation; its core methodology is precisely "replacing human judgment with model verifiers" — a combination of multiple verifiers + adaptive ARW weighting, essentially automating the approximation of human preference. But the paper also reveals the risk of this route (verifier hacking), indirectly demonstrating that human evaluation cannot be fully replaced.
【Pattern】The level of human investment correlates positively with the level of detail in data disclosure: ALIVE has both the most detailed data disclosure and the heaviest human investment; conversely, CCL/Baton have the least disclosure and no description of human involvement. This may reflect a consistent underlying trait: teams that prioritize data tend to both invest in human effort and disclose it in detail.

## Audio-Video Alignment

### Audio-Video Synchronization Detection Methods (lip-sync, event alignment) ⚠️

This batch of works falls into three tiers on synchronization detection, with a growing trend toward tool diversification:
【NAVA — three detectors used together (the most comprehensive in this batch)】
The audio-visual alignment operators in the data-filtering stage are explicitly three in parallel: "audio-visual alignment, measured by SyncNet, SyncFormer, and ImageBind" — SyncNet (lip-audio temporal synchronization, classic lip-sync detection), SyncFormer/Synchformer (a Transformer-based general audio-visual sync detector, able to handle non-speech event alignment), and ImageBind (cross-modal semantic similarity, measuring whether the audio and visual content are "about the same thing"). These three cover three distinct levels: SyncNet handles lip-audio timing, Synchformer handles general event timing, and ImageBind handles semantic matching — a well-layered alignment-detection system, far more complete than using SyncNet alone (as in Ovi or OmniCustom). None of the thresholds are disclosed [uncertain], the biggest regret in NAVA's data disclosure.
【OmniCustom — a single SyncNet dual threshold (thresholds fully disclosed)】
Follows the Ovi standard: "|offset|≤3" and "confidence >1.5." This set of values exactly matches Ovi's paper (|offset|≤3 frames, confidence>1.5), indicating that Ovi's thresholds have become the de facto reference standard in the field and have been directly inherited by subsequent work. At 24fps, |offset|≤3 frames corresponds to a time tolerance of ≤125 milliseconds. Applies only to lip-audio synchronization for clips containing speech, with no non-speech event-alignment detection [uncertain].
【ALIVE — TS-TalkNet for active-speaker detection (used for a different purpose than pure sync filtering)】
Uses TS-TalkNet (Target-Speaker TalkNet) "to evaluate the active speaker," producing a face-voice correspondence matrix. Note that its primary purpose is not "filtering out out-of-sync samples" but "determining who is speaking in a multi-person scene" — a harder task (active speaker detection rather than lip-sync verification). Another use of the sync score is selecting the identity anchor (the 1.5-second sub-clip with the highest sync score). The threshold is not disclosed, only that it "filters videos failing high-confidence thresholds" [the threshold value is uncertain].
ALIVE's audio-visual correlation judgment, in addition, is handled by an MLLM (see model_as_data_judge), forming a division of labor with TS-TalkNet's speaker detection: the MLLM handles semantic correlation, TS-TalkNet handles speaker attribution.
【StreamChar / CCL / Baton — no data-side sync filtering】
None of the three describe data-side synchronization detection [uncertain], instead relying on upstream datasets (SpeakerVid-5M / TalkVid / OpenHumanVid, which already have sync filtering built in) or on architectural guarantees. CCL reports the three sync metrics Sync-C / Sync-D / DeSync during evaluation, indicating it values synchronization, but places the guarantee on the architecture (TARP, the temporally-aligned RoPE) rather than on the data side.
【ITS-JAVG — moving sync detection to inference time】
Uses JavisScore as a fine-grained audio-video synchronization verifier ("focuses on fine-grained audio-video synchronization"), along with AVHScore to measure semantic consistency between audio events and visual events, and ImageBind to measure audio-video semantic similarity. The key finding is that guiding search with JavisScore alone causes other metrics to degrade (an asymmetric trade-off), and that the search will exploit the sync verifier's blind spots. This offers a direct lesson for the data side: filtering solely with a single SyncNet threshold would leave the retained data systematically biased toward SyncNet's preferences (e.g., favoring frontal faces and clearly visible lip movement), distorting the distribution — NAVA's use of three detectors together happens to mitigate exactly this problem. Author Joon Son Chung is himself one of the original authors of SyncNet, giving his judgment about the limitations of sync metrics particular authority.

### Specific Synchronization Detection Metrics and Thresholds (SyncNet/Synchformer/LSE/proprietary, threshold values, e.g., MOVA's LSE-D≤9.5 and LSE-C≥4.5, SkyReels-V4's SyncNet |offset|≤3∧conf>1.5) ⚠️

【Only one work fully discloses its thresholds】
OmniCustom: SyncNet "|offset|≤3" and "confidence>1.5" (identical to Ovi, directly inherited); combined with removal for aesthetic score <0.3 and duration <10 seconds. The three rules are combined with an AND relationship.

【ALIVE's related thresholds (not sync thresholds, but also data-filtering thresholds — the only set of numbers disclosed in this batch)】
The Character-driven cross-pair validity criteria:
- face similarity (ArcFace facial similarity) > 0.35
- CLIP similarity (CLIP visual similarity) > 0.7
- absolute proximity to 0.9
Identity-anchor selection: the 1.5-second sub-clip with the maximum sync score.
SubjectID correction: videos failing to meet "high-confidence thresholds" are filtered; the specific value is not disclosed [uncertain].
Other: cross-attention signal dropout probability of 0.3 during training; a FAISS retrieval similarity threshold of τ>0.85 at inference time.
TS-TalkNet's sync-score threshold is not disclosed [uncertain].

【NAVA】The list of detectors is public (SyncNet, SyncFormer, ImageBind) but "does not provide exact numerical thresholds" — none of the thresholds are disclosed [uncertain]. Likewise, the thresholds for the visual-quality operators (aesthetics, sharpness, brightness, motion score) and for AudioBox Aesthetic are also entirely undisclosed [uncertain]. This is a typical industrial paper: process description complete, numbers all withheld.

【StreamChar / CCL / Baton】No data-side sync thresholds [uncertain].

【Evaluation-side metrics (not filtering thresholds, but reflecting each work's measurement standard for synchronization)】
- CCL: Table 2 reports five metrics for ablation — WER, Sync-C, Sync-D, DeSync, and IB — Sync-C/Sync-D being SyncNet-family confidence and distance, DeSync being Synchformer-family desynchronization degree, and IB being the ImageBind score. Using five metrics together indicates a finer-grained measurement of synchronization than most works.
- NAVA: sets new SOTA for Sync-C / Sync-D / video quality / audio WER on Verse-Bench, with 2–5× fewer parameters than open-source baselines.
- ALIVE: Alive-Bench 1.0 contains 22 fine-grained metrics (across six major categories), synchronization presumably being one of them [details uncertain].
- ITS-JAVG: three sync-related verifiers — JavisScore (fine-grained synchronization), AVHScore (audio-visual event semantic consistency), and ImageBind (audio-visual semantic similarity); the ARW normalization formula is R(i)=Σ_k w_k·r_k(i)/(σ_k+ε).

【Cross-work observation】In 2026, threshold disclosure in this field polarizes into two camps: academic/mid-size teams (OmniCustom) disclose fully and directly follow the Ovi standard, while industrial teams (NAVA, ALIVE) disclose the process but withhold the numbers. SyncNet's |offset|≤3 / conf>1.5 has become a fixed community-default configuration.

### Separation of Temporal Synchronization vs. Semantic Synchronization (temporal alignment and content-semantic matching treated as two independent filtering criteria) ⚠️

In this batch, the awareness of separating "temporal alignment" from "semantic matching" has clearly grown, with NAVA and ALIVE each providing representative approaches:
【NAVA — three-layer separation on the data side + explicit separation on the architecture side (the clearest in this batch)】
(1) Data side: SyncNet (lip-audio timing), SyncFormer (general event timing), and ImageBind (cross-modal semantics) run in parallel — the first two handle timing, the last handles semantics, an explicit dual-track filter.
(2) Architecture side: NAVA's core argument is built directly on this separation — criticizing "unified tri-modal designs" for "conflating semantic and low-level alignment." Its Align-then-Fuse design is precisely meant to decouple the two: it first establishes low-level/fine-grained audio-video correspondence (native alignment) in a dedicated alignment space, then injects context (text, speaker embeddings) as an external condition via cross-attention (context as external conditioning) for semantics. This is the only work in this batch that elevates "separating temporal vs. semantic" to the level of a first architectural principle.
【ALIVE — audio-visual correlation as a filtering dimension independent of synchronization】
Audio quality filtering explicitly uses dual criteria: the first is the audio-quality score (noise), and the second is "audio-visual coherence" — the latter independent of TS-TalkNet's temporal sync detection, specifically judging whether the audio content is semantically relevant to the visual content, and on that basis collecting strongly correlated samples separately while controlling the proportion of weakly correlated samples such as BGM. This forms a very clear three-dimensional filtering space: temporal synchronization (TS-TalkNet) × semantic relevance (MLLM judgment) × audio quality (MLLM scoring). Particularly notable is that it does not blanket-remove weakly correlated samples but instead "controls the proportion" — acknowledging that non-diegetic sound (BGM, narration) is common in real content and the model needs the ability to generate it, while ensuring its proportion is not so high as to break the audio-visual causal relationship. This is more mature than the approach of works like Ovi, which "only filter on timing, leaving semantics implicitly bound via captions."
【OmniCustom】Only performs temporal filtering (the SyncNet dual threshold), with no semantic-matching filter — but given the nature of its task (single-person talking heads, where the audio must inherently belong to the on-screen person), the risk of semantic mismatch is naturally low, making this a reasonable omission.
【ITS-JAVG — splits the two into different verifiers at inference time and demonstrates their conflict】
Among its verifier combination, JavisScore measures fine-grained temporal synchronization, while AVHScore and ImageBind measure semantic consistency — the paper's core empirical finding is precisely that an asymmetric trade-off exists between these two objectives: optimizing temporal synchronization sacrifices semantic consistency, and vice versa, and no single verifier can achieve both. This provides direct quantitative evidence that "temporal and semantic alignment must be handled separately and explicitly balanced," and is the most theoretically valuable contribution in this batch to this problem. Its ARW algorithm essentially performs an adaptive trade-off between temporal-class and semantic-class rewards.
【CCL】In evaluation, reports both Sync-C/Sync-D (temporal), DeSync (temporal), and IB (ImageBind, semantic) together — the metrics distinguish the two, but there is no corresponding separated filtering on the data side [uncertain].
【StreamChar / Baton】Make no such distinction [uncertain]. Baton's planned tokens attempt to uniformly encode the semantic blueprint, with RS-RoPE responsible for temporal injection — an implicit division of labor architecturally (semantics via the planner, timing via RoPE), in the same vein as Ovi's approach of "RoPE handles timing, cross-attention handles semantics."

### Audio Quality Filtering (SNR, silence detection and silence-proportion thresholds, removal of tracks without audio, removal of off-screen sound sources, background-music separation) ⚠️

【ALIVE — replacing traditional signal-processing metrics with an MLLM (the most directionally significant approach in this batch)】
Original text: "We utilize an MLLM model ... to perform audio filtering based on two criteria. Firstly, for audio quality, the model assigns a score to each audio, allowing us to discard samples with significant background noise. Secondly, for audio-visual coherence, we assess the correlation ..."
(1) Audio quality: an MLLM directly scores each audio clip, and samples with significant background noise are removed on this basis — notably, no traditional audio-quality metric such as SNR, PESQ, or DNSMOS appears here at all; the task is handed entirely to a multimodal large model to "listen" and judge. This is the single point in this batch that most clearly represents the 2026 trend: audio-quality evaluation shifting from signal-processing metrics to large-model semantic judgment.
(2) Audio-visual coherence: correlation is assessed, with strongly correlated samples collected separately and the proportion of weakly correlated data such as BGM controlled "to optimize the dataset's composition."
(3) Not mentioned: SNR threshold, silence detection and silence proportion, removal of audio-less tracks (though the pipeline's first step already filters for "videos with audio," equivalent to removing audio-less tracks), source separation (not mentioned at all), and clipping/distortion detection [all uncertain].
【NAVA — AudioBox Aesthetic as the audio-quality operator】
Audio-quality filtering uses "AudioBox Aesthetic scores" (an audio-aesthetics evaluation model from Meta, producing a multi-dimensional audio-quality score). This is the only work in this batch to explicitly name a dedicated audio-quality model, closer to human perception than traditional SNR. There is also YAMNet-based audio classification for category tagging. Thresholds are not disclosed [uncertain]. No mention of SNR, silence, or source separation [uncertain].
【OmniCustom — format unification only, no quality filtering】
"We extract audio files from videos and unify them into 16kHZ" — audio is uniformly resampled to 16kHz, with no description of audio-quality filtering [uncertain]. Its filtering relies entirely on the SyncNet dual threshold (indirectly excluding samples with damaged audio: a damaged or silent track would cause SyncNet confidence to be extremely low, resulting in removal). This is a labor-saving approach of "implicitly using sync detection to also serve as audio-validity detection."
【StreamChar / CCL / Baton】No description of audio-quality filtering [uncertain]. CCL uses WavCaps and VGGSound for audio pretraining, both of which carry their own quality filtering; Baton uses AudioCaps + WavCaps similarly. All three outsource audio-quality control to the upstream sources.
【ITS-JAVG】At inference time, ImageBind-TA evaluates semantic coherence between text and generated audio, not an audio-quality metric — there is no dedicated audio-quality verifier at all, which is itself a gap: none of its six verifiers specifically measures audio fidelity/quality, potentially allowing the search to produce samples that are semantically correct but poor in audio quality [not discussed in the paper, an observation from this research].
【Overall judgment】The most notable change in audio-quality filtering in this batch is "de-signal-processing": ALIVE uses MLLM scoring, NAVA uses AudioBox Aesthetic (a learned perceptual model), both bypassing traditional metrics like SNR. Meanwhile, none of the seven use source separation (e.g., Demucs) — reflecting the mainstream consensus of preserving the native mixed audio track, since the goal is to generate a complete soundscape containing speech + sound effects + music.

### Classification and Differentiated Handling of Speech/Sound Effects/Music ⚠️

【ALIVE — a top-level speaking/non-speaking split driving the whole system (the most systematic in this batch)】
(1) The very top level of data organization is a binary split of audio type: "First, we make a top-level distinction between core scenarios: 'speaking' and 'non-speaking' scenario." — the corpus is first split by "whether someone is speaking," with the nine-domain three-tier tag system layered on top of it. This order matters: it shows that audio type is a higher-priority organizing dimension than visual domain, matching the essential needs of AV models (speaking scenes require lip sync and timbre consistency, non-speaking scenes require event-level audio-visual alignment — the modeling difficulty of the two is entirely different).
(2) Corresponding split at the caption level: <W> marks verbatim speech, <I> marks non-speech acoustic events, and the acoustic profiles within Subjects describe timbre attributes.
(3) BGM handled separately: as a representative of "weakly correlated" audio, its proportion is actively controlled rather than removed.
(4) Two-stage type switch in audio-tower training: Stage I pure speech (700k hours of transcribed speech, 1 epoch) → Stage II a mix of speech + real soundscapes (5k hours of high-quality speech + 111k hours of video audio tracks, 10 epochs).
(5) Among the nine Level-1 domains, Home Sounds and Sound Effects are dedicated to non-speech audio, and every Level-3 visual tag is bound to an audio keyword — visual concepts and sound concepts are indexed as pairs.
【NAVA — five audio tag classes (the finest classification in this batch)】
YAMNet + an omni-modal tagger divide the corpus into five categories: single-speaker speech, multi-speaker speech, ambient sound, music, and singing. Compared to the common three-way "speech/sound-effect/music" split, this five-way split has two particularly targeted refinements:
- Separating single-speaker from multi-speaker speech: directly serves its multi-speaker timbre-control capability (Timbre-in-Context Conditioning needs to know how many speakers there are and where each one's speech span is)
- Separating music from singing: singing carries both speech attributes (lyrics, timbre) and musical attributes (melody, rhythm), so listing it separately avoids polluting the modeling of pure speech and pure music
The audio section of the caption template is also described by the four categories speech / SFX / music / ambient sound. The training stage uses an "audio-only : audio-visual" ratio schedule (3:1 in Stage 1, 1:2 in Stage 2) to indirectly control exposure to each audio type.
【OmniCustom — a single type (pure speech)】All audio is single-person speech, with no sound-effect/music handling. The audio caption is organized by speaker attributes (age/gender/accent/pitch/prosody/emotion/speaking rate). This is the work with the most singular audio type in this batch, but also the one with the deepest timbre control as a result.
【StreamChar — speech-dominant】Emilia (a pure-speech multilingual dataset) is used for orchestrator pretraining, and the joint-training data is character talking video. No sound-effect/music type design [uncertain].
【CCL — general audio pretraining, speech-leaning joint training】Audio diffusion pretraining uses WavCaps (audio descriptions) + VGGSound (video sound effects), covering general sound effects; the joint-training data (OpenHumanVid + interviews/short dramas/films) is dialogue-dominant. This forms a structure of "general audio as base + speech-scene fine-tuning." Its multi-task probability distribution allocates 0.1 to text-to-audio and 0.15 to video-to-audio, indicating that pure audio-generation capability is explicitly preserved.
【Baton】AudioCaps and WavCaps provide general sound effects/soundscapes, OpenHuman-Vid provides human voice, with no explicit type-splitting strategy [uncertain].
【ITS-JAVG】The two tested foundation models have different audio-type emphases: MMDisCo is based on VGGSound (sound-effect-dominant), JavisDiT covers a broader range; among its verifiers, ImageBind-TA and AVHScore treat speech and sound effects the same way, with no type splitting [uncertain].

## Training Coordination

### Multi-Stage Training Curriculum and Data-Curriculum Scheduling (basis for stage division: resolution/duration/quality score/modality; low-res→high-res, image→video, short→long) ⚠️

【ALIVE — a seven-stage curriculum (the longest and most detailed in this batch, with the audio line and the audio-video line interwoven)】
Per the stage table given in the paper:
① T2A Stage I (audio-tower pretraining): 700k hours of transcribed speech / 384M audio samples, 1 epoch, lr 5e-5 — pure-speech base
② T2A Stage II (audio-tower mixed fine-tuning): 19M samples (5k hours of high-quality speech + 111k hours of video audio tracks), 10 epochs, lr 5e-5 — introduces real soundscapes; note the epoch count jumps from 1 to 10, with the high-quality data reused repeatedly
③ T2VA Joint-Train (joint audio-video training): 11M samples @480p/24fps, 1.2 epochs, lr 1e-4 — the highest-learning-rate stage, where the cross-modal connection is built from scratch
④ T2VA+I2VA (adding image conditioning): the same 11M samples, 0.3 epochs, lr 5e-5 — a brief capability expansion
⑤ Continue-Training (continued training on balanced data): 4.3M balanced samples, 3 epochs, lr 5e-5 — retraining for 3 epochs on a subset balanced via domain-mixture adjustment, a key stage for correcting distributional skew
⑥ SFT (supervised fine-tuning): 5M samples, high-aesthetics data mixed with realistic data at a 3:1 ratio, 0.5 epochs, asymmetric learning rates (video 1e-5 / audio 1e-6, with the audio side an order of magnitude lower to protect already-well-trained audio capability)
⑦ 1080p Refiner (high-resolution refinement): 0.7M high-clarity samples, 1 epoch, lr 5e-5
There is also a parallel Character-driven training pass (0.8M reference-paired samples).
The basis for curriculum division spans: modality (audio first, then audio-video) → conditioning type (T2VA→+I2VA) → data distribution (raw→balanced) → quality (→high-aesthetics SFT) → resolution (480p→1080p). The most dimension-rich curriculum design in this batch. The asymmetric learning rate (video 1e-5 / audio 1e-6) is a notable detail: it reflects that the two modalities reach different levels of maturity during joint training and need differentiated protection.
【NAVA — three stages, divided by modality mixture】
① Stage 1: audio-only : audio-visual = 3:1 — audio-dominant, first training up strong audio-generation capability
② Stage 2: the ratio flips to 1:2, "train on high-quality audio data together with the full audio-visual dataset" — high-quality audio + the full audio-visual dataset
③ Stage 3: fine-tuning on the filtered 160K high-quality audio-video subset
Total compute: "Approximately 107,520 H100 GPU-hours" across the three stages — the only work in this batch to publicly disclose total compute, a highly valuable reference point. Given the scale of a 6.3B model + 15M clips, this figure amounts to roughly 1,120 H100s training for 4 days, a mid-tier industrial scale.
The basis for division is purely "modality mixture + data quality," with no resolution or duration curriculum involved.
【CCL — two stages, extremely minimal】
① Audio-diffusion pretraining: 160,000 steps, batch 3200, lr 1e-4
② Joint audio-video training: the cross-modal attention parameters use lr 1e-4, the rest use lr 1e-5 (a differentiated learning rate — the newly added cross-modal modules learn fast, the already-pretrained parts learn slowly); the final setting is batch 320, 12,000 steps; the ablation stage uses batch 128, 6,000 steps
The video stream is initialized from pretrained Wan2.1-14B weights, while the audio stream is built from scratch (a similar architecture but with reduced channel dimensions). The entire joint training runs for only 12,000 steps — the core support for its "resource-saving" claim: compared to comparable works that often take tens of thousands of steps, CCL uses an order of magnitude less training volume to reach SOTA. GPU count and total GPU-hours are not disclosed [uncertain].
【StreamChar — two-stage pretraining + two-stage distillation】</content>
① Pretraining Stage 1 (orchestrator): Emilia dataset, 80k steps, batch 640, lr 6e-5
② Pretraining Stage 2 (joint training): 100k steps, batch 128, lr 1e-5
③ Distillation Stage I: 600 steps, compressing to a 4-step generator
④ Distillation Stage II: 400 steps, consistency fine-tuning under online chunk rollout, student lr 2e-6, fake-score-network lr 4e-7
The distillation stages total only 1,000 steps, almost negligible compared to the 180,000 steps of pretraining, indicating that distillation is a low-cost final mile of engineering.
【Baton — a three-stage progressive curriculum (built around decoupling the planner from the DiT)】
① Stage 1 (VA-Planner pretraining): target continuous features are extracted from the frozen penultimate layers of SigLip2 and WavTokenizer, and the planner is trained with L2 regression
② Stage 2 (DiT adaptation): the DiT receives ground-truth features projected through Latent-MLPs, trained with a flow-matching loss — deliberately using clean encoder features "to avoid confounding planner prediction noise"
③ Stage 3 (joint fine-tuning): the VA-Planner is frozen while the DiT remains trainable, and the DiT switches to receiving the planner's predicted features — "bridging the gap between clean features and imperfect predictions"
Total: 10 epochs, batch 1 per GPU, lr 1e-5. This "train on clean labels first, then switch to model predictions" three-stage design essentially addresses exposure bias (the same rationale as scheduled sampling), and is the most intricate curriculum design in this batch.
【OmniCustom】Training-stage division is not detailed [uncertain]; adopts LoRA fine-tuning (identity LoRA + timbre LoRA) combined with a contrastive-learning objective and flow matching, a lightweight adaptation atop an existing foundation model rather than multi-stage pretraining.
【ITS-JAVG】No training curriculum (training-free).

### Data-Mixture Changes Across Training Stages (pretraining/annealing/SFT high-quality subset) ⚠️

The explicitness of mixture scheduling varies enormously across this batch, with ALIVE and NAVA offering directly reusable numbers:
【ALIVE — three explicit mixture points】
(1) Speech/soundscape switch in the audio stage: Stage I is 700k hours of pure transcribed speech (384M samples); Stage II drops sharply to 5k hours of high-quality speech + 111k hours of video audio tracks (19M samples). Speech duration is compressed from 700,000 hours to 5,000 hours (1/140), while 111,000 hours of native video audio tracks are introduced — a dramatic distributional shift, moving from "massive speech to learn pronunciation" toward "curated speech to retain ability + massive real soundscapes to learn scenes." Stage II is trained for 10 epochs, indicating this mixed batch of data is highly valued.
(2) Aesthetic mixture ratio in the SFT stage: "high-aesthetics data mixed at 3:1 ratio with realistic data." This is the only explicitly disclosed SFT data-mixture number in this batch, meaning: the SFT stage deliberately lets high-aesthetics content dominate (75%), while still retaining 25% realistic content to prevent the model from becoming overly "filtered/influencer-styled" and losing realism.
(3) Balanced mixture in Continue-training: 11M → 4.3M "balanced samples," based on the nine-domain three-tier tag system and the two priors of "concept frequency + anticipated application scenarios." The specific proportion of each category is not disclosed [uncertain].
(4) Asymmetric learning rates as implicit mixture: in the SFT stage, video lr 1e-5 / audio lr 1e-6, with the audio side one order of magnitude lower — beyond loss weighting, learning-rate differences are used to control the "update mixture" between modalities.
【NAVA — an explicit reversal of modality mixture】
Stage 1 audio-only : audio-visual = 3:1 → Stage 2 flips to 1:2 → Stage 3, pure high-quality audio-video (160K). The logic of this curve is clear: first use a large amount of pure audio data to build solid audio-generation capability (audio data is cheap and abundant — the original pool has 20M audio clips), then gradually shift focus to the expensive paired audio-video data, and finally finish on a thousandth-scale premium subset. The absolute data volume of each of the three stages, and the proportion of each source (Koala-36M / TED / film-and-TV) at each stage, are not broken down [uncertain].
【CCL — multi-task probability mixture (the only work in this batch to give task-level sampling probabilities)】
During training, task type is randomly sampled by probability:
- text/image-to-video: 0.1
- text-to-audio: 0.1
- joint generation: 0.6
- audio-to-video: 0.15
- video-to-audio: 0.15
Summing to 1.0. Joint generation, at 60%, is the overwhelming majority; the two cross-modal conversion tasks (A2V, V2A) each take 15% — these two tasks serve to reinforce cross-modal conditional dependency (the model must truly "understand" one modality to generate the other), a key regularizer preventing the dual streams from degenerating into two independent generators. Each single-modality task takes 10%, used to keep single-modality ability alive. This mixture is a major reason CCL can reach SOTA with only 4M data: through multi-task mixing, the same batch of data is reused in five different ways, substantially amplifying its effective data efficiency.
【Baton】The data mixture across the three stages is not broken down [uncertain]; the proportions of the four sources within the 1.5M clips — OpenHuman-Vid / AudioCaps / WavCaps / internet videos — are not disclosed [uncertain].
【StreamChar】Emilia (pure speech) is used for Stage 1, and the audio-video datasets for Stage 2, with the two stages drawing on entirely different sources and no blended mixture [the mixture among the three audio-video datasets is uncertain].
【OmniCustom】A single dataset, so no mixture issue arises; but its fixed "first 4 seconds reference + last 5 seconds training" split is itself a mixture design along the time dimension.
【ITS-JAVG】No training mixture; but its ARW algorithm addresses precisely "how multiple reward signals should be weighted and aggregated" — mathematically homologous to training-data mixture (both are weighted-combination optimization over multiple sources). Its variance-adaptive weighting idea could in principle be transplanted to data-mixture scheduling (adaptively adjusting sampling weight by the gradient variance of each domain), though the paper does not pursue this extension.

### Post-Training Data (scale and selection criteria of the SFT curated subset, number of preference pairs and annotation method, reward-model training data) ⚠️

The post-training form across this batch is dominated by "high-quality subset SFT," with none adopting preference learning/RLHF:
【NAVA — a thousandth-scale curated SFT (the most typical in this batch)】
From the 15M-clip training corpus, "multi-operator collaborative filtering" produces 160K high-quality samples, with the selection criteria being "accurate captions and strong audio-visual alignment." The SFT retention rate is about 1.07% — i.e., ten out of every thousand clips. Moreover, this subset's captions are regenerated by the more expensive Gemini-3-Pro ("to produce more accurate, structured, and temporally grounded audio-visual captions"), rather than reusing the original Flash-generated captions. This double purification of "curated subset + upgraded captions" is a notable practice: the SFT stage upgrades not just the data but also the annotation quality. Specific thresholds are not disclosed [uncertain]. No preference pairs, no reward model, no RLHF [uncertain].
【ALIVE — multi-layer post-training but no preference learning】
(1) Continue-Training: 4.3M balanced samples, 3 epochs — a transitional stage between pretraining and SFT, using a domain-balanced subset to correct distributional skew.
(2) SFT: 5M samples, high-aesthetics and realistic data mixed 3:1, 0.5 epochs, asymmetric learning rates (video 1e-5 / audio 1e-6). Note that it trains for only 0.5 epoch — the SFT stage is deliberately kept shallow to avoid overfitting to the high-aesthetics distribution at the expense of diversity.
(3) 1080p Refiner: 0.7M high-clarity samples, 1 epoch — an independent high-resolution refinement module, itself also a form of targeted post-training.
(4) Character-driven: 0.8M reference-paired samples (data constructed via cross-pair and in-pair augmentation) — dedicated post-training for reference-character capability.
No description of DPO/RLHF/preference pairs/reward model [uncertain]. Human evaluation (blind comparison against Veo 3.1 / Kling 2.6 / Wan 2.6 / Sora 2 / LTX-2) is used only for assessment, not fed back as a training signal [uncertain].
【StreamChar — distillation as post-training】
Two-stage distillation: Stage I, 600 steps, compressing step count (→ a 4-step generator); Stage II, 400 steps, "rollout consistency" (fine-tuning the student under online chunk rollout), student lr 2e-6, fake-score-network lr 4e-7. Stage II's training data is the student model's own online rollout — an on-policy self-generated form, the only post-training approach in this batch involving "model output fed back into training." Ablation shows single-stage distillation underperforms the two-stage approach.
【OmniCustom — LoRA adaptation as post-training】
Trains an identity LoRA and a timbre LoRA on top of an existing joint audio-video foundation model, combined with a contrastive-learning objective (the prediction stream with reference conditioning as positive, without reference conditioning as negative) and flow matching. The training data is the paired samples of OmniCustom-1M. No independent preference data or curated subset [uncertain].
【CCL / Baton】No post-training stage [uncertain]. CCL's 12,000-step joint training is itself the final stage; Baton's Stage 3 joint fine-tuning (planner frozen, DiT fine-tuned) can be viewed as generalized post-training, but with no preference data.
【ITS-JAVG — replacing post-training with inference-time search (the most instructive point in this batch)】
Its core claim is precisely that quality can be improved without post-training at all — using multiple verifiers + Best-of-N/EvoSearch to select the best at inference time (JavisDiT 5 samples, MMDisCo 10 samples), with effects comparable to training-side optimization. This effectively proposes an alternative path: rather than spending on SFT/RLHF, sample more at inference time and filter with verifiers. Conversely, its high-scoring selected samples are a ready-made source for constructing SFT/preference data (high scores as positives, low scores as negatives), though the paper does not take this step.
【Common gap】None of the seven use preference pairs/RLHF/DPO — a stark contrast with contemporaneous closed-source industrial models (Sora 2, Seedance, etc.), which generally include an RLHF stage, reflecting that preference alignment remains a blank area on the open-source/academic side of JAVG. The verifier-hacking problem revealed by ITS-JAVG also foreshadows: rashly using automatic verifiers to construct preference data for RLHF would very likely train a model that only knows how to please the judges.

### Data-Processing Infrastructure and Throughput (NeMo Curator/Data-Juicer/proprietary, GPU acceleration ratio, processing scale, cost) ⚠️

Disclosure is sparse but contains two high-value data points:
【NAVA — the only work to publicly disclose total compute and segmentation infrastructure】
(1) Total compute: "Approximately 107,520 H100 GPU-hours" across the three training stages. This is the only compute figure in this batch, and a rare instance of transparent disclosure among contemporaneous JAVG papers. Converted: roughly 1,120 H100s training continuously for 4 days, or 512 H100s training for about 8.75 days. For a configuration of a 6.3B model + 15M clips, this is a mid-tier industrial scale — by comparison to contemporaneous large-company video models that often run into hundreds of thousands or even millions of GPU-hours, NAVA is fairly conservative.
(2) Data-segmentation infrastructure: "raw videos are first segmented at scale with a Hadoop-based pipeline" — processing the segmentation of 100M videos with a Hadoop distributed pipeline. Choosing Hadoop (rather than Spark, Ray, or a GPU-accelerated framework) indicates that its data processing is dominated by CPU-intensive I/O and transcoding.
(3) Deduplication infrastructure: VideoCLIP embedding extraction + "large-scale k-means clustering" — performing embedding clustering at a scale of 100 million videos is itself a significant engineering challenge, but the specific implementation (whether FAISS is used, the distributed scheme, the time cost) is not disclosed [uncertain].
(4) Inference side: 8-way sequence parallelism generates about 1 minute of video; weights are 24GB (bf16) / about 7GB (fp8 quantized).
【ALIVE — FAISS retrieval infrastructure (inference side)】
Builds a dense vector index using FAISS: "We first construct a dense vector index ... using FAISS ... extract sound events from the user's prompt and query this database for the nearest neighbors based on cosine similarity," with a retrieval similarity threshold of τ>0.85. This is prompt retrieval-augmentation at inference time rather than training-data processing, but it likewise belongs to data infrastructure. The training-side cluster scale, GPU type, GPU-hours, data throughput, and processing cost are all undisclosed [uncertain]. Given its scale of 384M audio samples + 11M video samples, the compute investment should far exceed NAVA's, but no figure is given.
【CCL — indirectly demonstrating "efficiency" through training scale】
Although GPU count and GPU-hours are not disclosed [uncertain], its core selling point is precisely resource efficiency: training data of 4M (vs. Ovi's 30.7M, MOVA's 50M), with joint training of only 12,000 steps @batch 320. The paper states it "achieves state-of-the-art performance with substantially reduced computational resources compared to recent academic approaches." At batch 320 × 12,000 steps ≈ 3.84 million sample-instances, this training volume is indeed extremely small. Initializing the video stream from Wan2.1-14B is the precondition for this savings — standing on a strong foundation model, it only needs to learn the cross-modal connection.
【StreamChar — real-time performance at inference is its core engineering metric】
Runs in real time on a single H100 GPU, each chunk 33 frames @24fps. This is the only work in this batch to make "real-time performance" its top engineering priority, and its two-stage distillation (4-step generator) exists exactly for this purpose. No data-processing infrastructure is disclosed [uncertain].
【OmniCustom / Baton】No data-infrastructure disclosure [uncertain]. Baton only gives batch size 1 per GPU, lr 1e-5, 10 epochs — batch 1 per GPU indicates tight single-GPU memory (the Qwen3-8B planner and the DiT are in memory simultaneously), but total GPU count is not stated [uncertain].
【ITS-JAVG — inference cost is its price to pay】
The essence of ITS is trading inference compute for quality: JavisDiT generates 5 candidates per prompt, MMDisCo generates 10, plus the scoring overhead of 6 verifiers — inference cost is amplified 5–10× or more compared to a single generation. The paper's value proposition is that this expense is far lower than the cost of retraining a model. Specific latency/throughput figures could not be extracted [uncertain].
【Common pattern】None of the seven use off-the-shelf data-processing frameworks such as NeMo Curator or Data-Juicer, all being self-built or directly reusing public datasets; only NAVA names general infrastructure such as Hadoop and k-means.

## Results Comparison

### Quantified Impact of Data-Strategy Ablations (distinguishing: filtering-strictness ablation / caption density-style ablation / data-mixture ablation, and the corresponding evaluation metrics) ⚠️

The ablations in this batch are generally concentrated on architectural modules, with genuine data ablations being extremely rare — a shortfall shared by all seven:
【Six works with no data ablation】
- ALIVE: "The paper contains no ablation studies isolating the impact of individual pipeline stages" — none of the six data-pipeline stages is individually ablated and verified. Given that its pipeline is the most complex in this batch (especially the costly five-step SubjectID correction sub-pipeline), the absence of a "with/without SubjectID correction" comparison is the most regrettable omission. Similarly, the benefits of the 13-dimensional quality classifier, the six-tier clarity filter, and the nine-domain mixture adjustment are all unquantified.
- NAVA: "No ablation studies on data composition are presented" — ablations focus on architecture (the number of Align-then-Fuse layers) and guidance mechanisms, with no data-side ablation. The benefits of the 3:1 → 1:2 modality-mixture schedule and the 160K SFT subset are without controlled experiments.
- OmniCustom: no data ablation [uncertain]; the individual contribution of each of its three filtering rules (the SyncNet dual threshold, aesthetics <0.3, duration <10s) is not verified.
- StreamChar: ablations appear in Tables 1–2, all architecture/system side — the most valuable one is the sink-chunk (persistent visual anchor) ablation: removing it worsens drift from 0.0067 to 0.0304, a roughly 4.5× degradation, quantitatively proving the visual anchor's decisive role in long-range consistency. There is also a comparison of single-stage vs. two-stage distillation. No data-side ablation.
- Baton: Table 2 ablates the VA-Planner's components, and Table 3 ablates RS-RoPE and backbone variants — all architecture side. But one design choice highly relevant to data/annotation paradigm is argued: continuous-feature regression vs. discrete-token prediction, with the paper claiming "regressing continuous features preserves richer semantic structure"; if Table 2 contains this comparison it would constitute empirical evidence for "the form of semantic intermediary representation" [specific numbers not extracted, uncertain].
- CCL: Table 2 reports ablation results, with metrics WER / Sync-C / Sync-D / DeSync / IB across five metrics, ablating the four modules TARP, LCT, DCR, and UCG — all architecture side. However, Table 1's side-by-side comparison (CCL 4M vs. Ovi 30.7M vs. MOVA 50M), while not a strict ablation, is the most compelling piece of "data efficiency" evidence in this batch (see quality_over_quantity_evidence). The ablation training configuration is 6,000 steps @batch 128, versus the final configuration of 12,000 steps @batch 320.
【The only systematic study of the effect of "verifier selection": ITS-JAVG】
Although not a training-data ablation, its systematic ablation of "verifier combinations" is methodologically equivalent to an ablation of "data-filtering scorer combinations," making it the closest thing to a data ablation in this batch:
(1) Single verifier vs. multiple verifiers: demonstrates that "single-verifier guidance effectively improves its intended evaluation metrics, yet fails to achieve a balanced improvement across all metrics" — a single scorer can only improve the metric it itself measures, while other metrics may instead degrade (an asymmetric trade-off).
(2) Empirical evidence of verifier hacking: the search algorithm will "exploit blind spots" (exploit the scorer's blind spots), degrading along dimensions the scorer cannot see.
(3) Identification of the optimal verifier combination: one of the paper's contributions is finding a combination of verifiers that yields balanced improvement.
(4) The benefit of ARW: compared to fixed-weight reward aggregation, adaptive weighting (normalizing by the variance of each reward) yields more balanced improvement.
This set of conclusions directly implies for training-data pipelines: filtering with a single aesthetic score or a single SyncNet threshold will leave retained data systematically biased toward that scorer's preferences and will degrade along its blind spots (such as audio quality, semantic plausibility); multi-operator collaboration (such as NAVA's triple alignment operators SyncNet+SyncFormer+ImageBind) is in principle more robust.
【Overall judgment】This batch of H1 2026 JAVG works is nearly blank on data ablation — none performed a "filtering-strictness ablation," a "caption density/style ablation," or a "data-mixture ablation." The effectiveness of data strategies rests mainly on engineering intuition backed by final metrics, lacking traceable causal evidence. This stands in sharp contrast to the engineering complexity of the data side in the same batch (ALIVE's six-stage pipeline, NAVA's multi-operator filtering) — the pipelines keep getting more complex, but no one verifies whether every step is worth it.

### Evidence of Quality vs. Quantity (cases where small, curated data outperforms large, mixed data) ⚠️

【CCL — the most direct, most quantified evidence in this batch of "small and precise beats large and mixed"】
Table 1 explicitly lists the three-way comparison of training data volume: CCL 4M vs. Ovi 30.7M vs. MOVA 50M — CCL uses about 1/8 of Ovi's data volume and about 1/12 of MOVA's, combined with just 12,000 steps of joint training (batch 320), to reach SOTA performance. The paper states it "achieves state-of-the-art performance with substantially reduced computational resources compared to recent academic approaches, while requiring minimal training data by leveraging pre-trained diffusion models."
It should be objectively noted that CCL's efficiency does not come purely from "higher data quality," but from a combination of three factors:
(1) Strong-foundation transfer: the video stream is initialized from pretrained Wan2.1-14B weights — most of the visual prior is inherited for free, so its 4M data only needs to learn the cross-modal connection rather than learning video generation from scratch.
(2) A narrow but deep domain: its data sources (OpenHumanVid + interviews + short dramas + films) are highly concentrated on "narrative content with people talking," trading breadth for density within that domain.
(3) Multi-task reuse: five tasks are sampled by probability (joint 0.6, A2V 0.15, V2A 0.15, T2V/I2V 0.1, T2A 0.1), with the same batch of data reused in five different ways, multiplying its effective data efficiency.
Therefore, a more precise formulation is: "a strong foundation + a narrow domain + multi-task reuse" can compress the data requirement by an order of magnitude — an extremely valuable route for resource-constrained teams.
【NAVA — evidence on the parameter-efficiency side + a thousandth-scale SFT purification】
(1) Parameter efficiency: 6.3B parameters reach SOTA on Sync-C / Sync-D / video quality / audio WER on Verse-Bench, while "using 2× to 5× fewer parameters than open-source baselines."
(2) Extreme data-purification ratio: 15M → a 160K SFT subset (a retention rate of about 1.07%), with that subset's captions regenerated by the more expensive Gemini-3-Pro. This "thousandth-scale curation + annotation upgrade" is itself a strong quality-first statement — but the paper does not run a "with/without the 160K SFT stage" controlled experiment [uncertain], so the benefit cannot be quantified.
(3) Strict filtering: 100M videos → 15M (about 15% retention), showing the team is willing to discard 85% of the data.
【OmniCustom — strict filtering in exchange for customization quality】
Filtered from SpeakerVid-5M's 5.2M clips / 8,000 hours down to 1M clips / 2,500 hours (a 19% clip-level retention rate, 31% hour-level retention rate), retaining only clips with good synchronization (SyncNet |offset|≤3 and conf>1.5), aesthetic score ≥0.3, and duration ≥10 seconds. Preparing high-purity data for the high-precision task of identity+timbre customization is a typical quality-first orientation. But there is no "loose vs. strict filtering" comparison [uncertain].
【ALIVE — counter-evidence: scale remains the primary lever】
ALIVE takes the opposite route: 700k hours of speech, 11M joint samples, 384M audio samples — winning through sheer absolute scale, while also using an extremely complex six-stage pipeline to ensure quality. Its "11M → 4.3M balanced" balancing reduction (39% retained) and the "5M SFT with high-aesthetics:realistic = 3:1" mixture show that it performs fine-grained distributional control on top of scale — a case of "scale and quality both, together" rather than an either/or choice.
【StreamChar — evidence of generalizing from short training to long inference】
Training data is entirely ≤20 seconds, yet it can generate a continuous 5-minute stream — another form of "doing more with less": relying not on long-video data but on architectural mechanisms (the progress-aware pointer + persistent visual anchor) to achieve long-range generalization. The sink-chunk ablation (drift 0.0067 vs. 0.0304) proves this route is viable. The lesson for the data side is that some capabilities (long-range consistency) may be more economically solved with architecture than with data (collecting long videos).
【ITS-JAVG — the most radical "zero training data" stance】
Fully training-free, using multi-verifier search at inference time to gain quality improvement — shifting "quality" away from both the data side and the training side entirely onto the inference side. This is the most thorough challenge in this batch to the assumption that "more data = a better model." But the cost is a 5–10× amplification of inference cost, and the paper itself reveals the risk that verifiers can be exploited.
【Baton】At 1.5M clips, the smallest scale among the joint-generation works in this batch; its performance gains are attributed to the VA-Planner's semantic planning rather than to data — likewise a route of "using method to compensate for data," but without a data-volume controlled experiment [uncertain].

### Alignment Between Training-Data Domain Distribution and Evaluation-Benchmark Taxonomy (e.g., VABench's seven major categories) ⚠️

【ALIVE — partial alignment between the training tag system and the evaluation taxonomy (the closest to a closed loop in this batch)】
(1) Training-side taxonomy: the top-level speaking/non-speaking split plus the nine-Level-1-domain three-tier hierarchy (Animals, Home Sounds, Entertainment, Environment, Food, Nature, Sound Effects, Vehicles, Sports), with each category's proportion actively adjusted based on "concept frequency + anticipated application scenarios."
(2) Evaluation-side taxonomy: Alive-Bench 1.0 contains 264 general prompts, "covers a wide range of scenarios, including single-person speech, multi-people conversations, sports, daily activities, animals" — single-person speech, multi-person conversation, sports, daily activities, animals, and so on; plus 90 reference-character prompts specifically testing reference-character capability. Evaluation covers both Chinese and English.
(3) Alignment relationship: the evaluation taxonomy clearly overlaps with the training-side Level-1 domains (sports↔Sports, animals↔Animals, daily activities↔Home Sounds/Food), and the distinction between "single-person speech vs. multi-person conversation" directly corresponds to the training side's speaking/non-speaking split and the multi-person scenarios targeted by SubjectID correction. ALIVE can be said to be the work in this batch with the clearest correspondence between training distribution and evaluation taxonomy.
(4) The 22 fine-grained metrics fall into six major categories [specific categories not extracted, uncertain]; no results are seen reported grouped by domain, so the alignment remains at the "taxonomy-design level" rather than the "results-reporting level" [uncertain].
【NAVA — training classification and evaluation benchmark are not aligned】
The training side organizes the corpus using the five YAMNet audio tag classes (single-speaker speech / multi-speaker speech / ambient sound / music / singing); evaluation instead uses Verse-Bench (derived from UniVerse-1) and Seed-TTS, both of which are "quality-dimension" evaluations rather than "content-taxonomy" evaluations. Verse-Bench reports Sync-C / Sync-D / video quality / audio WER, and Seed-TTS reports speech metrics. The training-side five audio tag classes have no corresponding grouping in evaluation [uncertain]. The user study covers four dimensions — video quality, audio-video synchronization, audio fidelity, and timbre controllability — of which "timbre controllability" directly echoes the training-side single-/multi-speaker distinction and the Timbre-in-Context design, the only point of alignment.
【OmniCustom — the evaluation-set design is deliberately "counter-aligned" with the training data】
The composition of the 100-example evaluation set is deliberate: 30 real people outside the training set + 70 YouTube video segments, with a 1:1 gender ratio. Deliberately choosing identities absent from the training data is exactly meant to verify zero-shot timbre/identity transfer — i.e., the evaluation set is deliberately non-overlapping with the training distribution along the identity dimension. This is a "reverse alignment": rather than pursuing distributional consistency, it pursues verification of out-of-distribution generalization. The 1:1 gender control is the only explicit demographic-mixture control on the evaluation side.
【CCL — a fine-grained metric system but no taxonomy alignment】
Evaluation metrics WER / Sync-C / Sync-D / DeSync / IB, five in total, covering speech intelligibility, lip-audio synchronization (two SyncNet-family metrics), general audio-visual synchronization (Synchformer-family), and cross-modal semantics (ImageBind) — a very fine-grained metric division that happens to correspond to the "separating temporal vs. semantic matching" idea. But the training data's domain (interviews/short dramas/films) has no corresponding grouped reporting in evaluation [uncertain].
【StreamChar — evaluation design tightly tied to its long-horizon streaming positioning】
On the EMTD dataset, "150 clips generating 10s audio-video pairs" (short-horizon capability) + "50 clips paired with randomly sampled transcripts (>300 words) to produce 5-minute continuous streams" (long-horizon streaming capability) — evaluation deliberately designs both a short and a long tier, with the long tier (5 minutes, >300-word transcripts) far exceeding the training data's 20-second cap, a targeted test of generalization ability. Human evaluation involved 24 people × 50 cases. There is no correspondence between the evaluation taxonomy and the training data's domain distribution (both are entirely people talking, a single category).
【Baton — self-built Sem100 to supplement the semantic-reasoning dimension】
Beyond Verse-Bench, it self-builds Sem100: "100 unseen videos (10 seconds long) with more complex prompts, selected from the internet to assess the semantic reasoning capability" — 100 unseen 10-second videos paired with more complex prompts, specifically to evaluate semantic reasoning capability. This benchmark is tailor-made to verify the VA-Planner's semantic-planning advantage, i.e., the evaluation benchmark is aligned with the methodological claim (rather than with the training-data distribution). Construction details are not disclosed [uncertain].
【ITS-JAVG — the circularity risk between evaluation benchmark and verifiers (the point most worth being wary of in this batch)】
Evaluation uses JavisBench-mini (testing JavisDiT) and the VGGSound test set (testing MMDisCo). A structural problem exists: its verifiers (JavisScore, ImageBind, AVHScore, etc.) overlap heavily with, or are even the same as, the evaluation metrics — using a given metric as the verifier to guide the search, then using that same metric to evaluate the result, will inevitably show "improvement." The paper is clear-eyed about this, which is exactly the motivation behind its verifier-hacking concept and multi-verifier-combination proposal: only when the set of verifiers being optimized against does not fully overlap with the set of metrics being evaluated is the improvement genuine. This methodological warning applies equally to the data side — if the same model used for data filtering (e.g., filtering data with SyncNet) is also used for evaluation (e.g., evaluating with Sync-C), part of the resulting improvement is circular reasoning. In this batch, both NAVA (filtering with SyncNet, evaluating with Sync-C/Sync-D) and OmniCustom (the same situation) carry this potential circularity, and neither paper discusses it [uncertain].
